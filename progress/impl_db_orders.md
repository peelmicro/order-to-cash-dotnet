# impl_db_orders — feature 9, phase 6

## What was built

An EF Core 10 `DbContext` (`OrdersDbContext`) for `otc_orders`, covering every table in
Databases doc §4: the four seeded reference catalogues (§4.1), the `orders`/`order_items`
persistence rows and `order_number_sequences` (§4.2), the reliability tables `outbox` and
`processed_events` (§4.3), and the saga orchestrator's durable state, `saga_commands` and
`saga_ignored_facts` (§4.4) — eleven tables in total. One migration (`InitialCreate`) creates
all of them, plus every index the Databases document names.

This is schema-only, by design: the `Order` domain aggregate lands separately in feature
`orders_aggregate` (phase 8). The persistence types in `Infrastructure/Persistence/Entities/`
are plain POCOs (e.g. `Order`, `OrderItem`), not the domain aggregate — there is no `Domain/`
code in this feature, and none is reachable from `Infrastructure/`, so `DomainPurityTests`
(unmodified, in `tests/Architecture.Tests/`) still passes cleanly.

## What could not be done, and why

Nothing from the acceptance list was skipped. One thing outside its scope: `order_items.order_id`'s
FK-generated index and the `PK_*` clustered indexes exist but are not spec-named, so they are not
asserted — only the eleven indexes the Databases document actually names are.

## What surprised me

- **`order_number_sequences.id` is not a UUID.** Every other table's PK is a domain-generated
  `UniqueId`/`uniqueidentifier`, but the Databases doc describes this table as `id = 1` — a
  well-known technical row, not a business entity — so I modeled `Id` as `int` with
  `ValueGeneratedNever()`. This is the one place the general "primary keys are UUIDs" convention
  in the Databases doc's §3 does not apply, and the doc itself signals it by writing a literal `1`
  rather than a placeholder UUID.
- **MS-SQL's default `datetime2` precision is 7, not 3.** EF Core's SQL Server provider maps
  `DateTime` to `datetime2(7)` unless told otherwise — every single date/time column needed an
  explicit `.HasColumnType("datetime2(3)")`; there is no MS-SQL provider-level default that gets
  this right for free the way #7's MySQL `datetime(3)` column type declares it directly.
- **`Testcontainers.MsSql`'s parameterless `MsSqlBuilder()` constructor is now obsolete** (as of
  4.14.0) and fails the build under `TreatWarningsAsErrors`; had to pin the image explicitly to
  `mcr.microsoft.com/mssql/server:2022-CU26-ubuntu-22.04`, matching `docker-compose.infra.yml`'s
  own `mssql` service tag, which is arguably better anyway — the integration tests now validate
  against the exact same engine build the compose stack runs, not whatever Testcontainers used
  to default to.
- **The migration was verified twice over**: once via Testcontainers against a disposable
  container, and once with `dotnet ef database update` directly against the running
  `otcnet-mssql` compose container's real `otc_orders` database (idempotent re-run confirmed:
  "No migrations were applied. The database is already up to date.").

### D1 (BLOCKING) — seven of eight foreign keys were missing

**What it was:** every `FK →` annotation in Databases doc §4.1/§4.2 except `order_items.order_id`
was silently dropped. The POCOs carried the FK columns (`currency_id`, `company_id`,
`retailer_id`, `product_id`) as bare `Guid`s with no `HasOne`/`HasForeignKey` in the
corresponding `IEntityTypeConfiguration<T>`, so EF never emitted the constraint. Live
`sys.foreign_keys` returned exactly one row before the fix.

**Fix:** added the seven missing relationships, each `HasOne<TPrincipal>().WithMany().HasForeignKey(...).OnDelete(DeleteBehavior.Restrict)`
— deliberately the generic `HasOne<T>()` form with no navigation-property argument on either
side, so EF does not invent a navigation property beyond what §4 documents:

  - `src/Orders/Infrastructure/Persistence/Configurations/ProductConfiguration.cs` — `currency_id → currencies.id`
  - `src/Orders/Infrastructure/Persistence/Configurations/RetailerConfiguration.cs` — `currency_id → currencies.id`
  - `src/Orders/Infrastructure/Persistence/Configurations/CompanyConfiguration.cs` — `currency_id → currencies.id`
  - `src/Orders/Infrastructure/Persistence/Configurations/OrderConfiguration.cs` — `company_id → companies.id`,
    `retailer_id → retailers.id`, `currency_id → currencies.id`
  - `src/Orders/Infrastructure/Persistence/Configurations/OrderItemConfiguration.cs` — `product_id → products.id`

`order_items.order_id → orders.id` (cascade) was already correct and is unchanged.

**New test:** `tests/Orders.IntegrationTests/ForeignKeyTests.cs` —
`Exactly_The_Eight_Spec_ForeignKeys_Exist_With_The_Right_Reference_And_DeleteAction`. Reads
`sys.foreign_keys` + `sys.foreign_key_columns` + `sys.tables`/`sys.columns` on the real database
(never EF's model) and asserts: exactly 8 rows, each with the exact `(table, column) →
(referenced table, referenced column)` pair, each delete action (`NO_ACTION` for all seven
`Restrict` FKs, `CASCADE` for `order_items.order_id`), and fails on any *extra* FK not in the
spec's eight (`unexpected foreign key(s) not in the spec`), not just on a missing one.

**Live verification** (the reviewer's own method, re-run after the fix, against the composed
`otcnet-mssql` / `otc_orders`, not a disposable Testcontainers instance):

### D2 (BLOCKING) — `order_number_sequences.next_value` was `bigint`, spec says `int`

**What it was:** `OrderNumberSequence.NextValue` was `long` (→ `bigint`), and
`SchemaColumnTypeTests.cs` asserted `"bigint"` — the wrong value was locked in by the guard meant
to catch exactly this kind of drift.

**Fix:**
- `src/Orders/Infrastructure/Persistence/Entities/OrderNumberSequence.cs` — `NextValue` changed
  from `long` to `int`, with an XML doc comment citing Databases doc §4.2 verbatim and #7's
  `order-number-sequences.schema.ts:20` so the reasoning is on the type itself, not just in this
  report.
- `tests/Orders.IntegrationTests/SchemaColumnTypeTests.cs` — expected type for
  `order_number_sequences.next_value` changed from `"bigint"` to `"int"`.

No configuration change was needed beyond the entity: `int` → SQL Server `int` is EF's default
mapping (no `HasColumnType` override, consistent with every other plain `int` column in this
model).

**Live verification:** `SELECT DATA_TYPE FROM INFORMATION_SCHEMA.COLUMNS WHERE
TABLE_NAME='order_number_sequences' AND COLUMN_NAME='next_value'` against the composed
`otc_orders` → `int`.

This table's neighbour, `id`, stays `int` (unchanged) — that one *is* a legitimate translation
(§4 gives no type for it, only the literal `1`), and was already disclosed and reasoned about in
the original report; the standard D2 asked `next_value` to meet.

### Corrected divergence list (the previous report claimed completeness it did not have)

What is **actually** different from the Databases doc / #7's DDL now, after the fix pass — this
is the honest version the first report should have contained:

1. **`order_number_sequences.id` is `int`, not a UUID.** Disclosed and reasoned about in both
   submissions; §4 gives this table's `id` no type, only the literal `1`, and #7 itself uses
   `tinyint` there (also not a UUID) — the reviewer confirmed this meets the bar D2 needed.
2. **`payload` (in `outbox` and `saga_commands`) is `nvarchar(max)`, not MySQL `json`.** MS-SQL
   2022 has no native JSON column type; `nvarchar(max)` preserves insertion order, which is the
   `CLAUDE.md`/feature-8 ruling on wire-shape parity (payload asserted semantically, not by
   storage-column byte order).
3. **`Order`/`OrderItem`/etc. are plain persistence POCOs, not the domain aggregate.** No
   `Domain/` code exists in this feature by design; `orders_aggregate` (phase 8) owns the
   aggregate and will map to/from this schema.
4. **Non-spec-named indexes exist** (7 EF-generated single-column indexes on the FK columns just
   added, e.g. `IX_orders_company_id`, plus the pre-existing `IX_order_items_order_id`, plus the
   `PK_*` clustered indexes). None of these were requested by the Databases doc, none are
   asserted by `IndexTests`, and none conflict with anything the doc does name — they are simply
   what EF creates so a foreign key has a supporting index, and dropping them would be a separate,
   unrequested optimization.

Everything else — every table, every column type, every named index, every unique constraint, and
now every foreign key — matches Databases doc §4 and #7's DDL, verified against the live
database, not against this project's own model.
