# impl_db_billing — feature 11, phase 6 (closes Phase 6)

## What was built

Two EF Core 10 `DbContext`s, both schema-only (no domain aggregates), matching features
`db_orders`/`db_fulfillment`'s established pattern:

1. **`BillingDbContext`** for `otc_billing` (Databases doc §6): `credits`, `credit_items`,
   `invoices`, `invoice_items`, `payments`, `invoice_number_sequences`, plus the reliability
   tables `outbox` and `processed_events` (§4.3) — 8 tables, one migration (`InitialCreate`).
2. **`NotificationsDbContext`** for `otc_notifications` (Databases doc §7): **`processed_events`
   and nothing else** — no outbox, because the Notifications service produces no facts, only
   consumes them. One table, one migration (`InitialCreate`).

Plus this feature's distinctive deliverable: **`ReliabilityTableParityTests`**, the .NET
equivalent of #7's `apps/seed/outbox-parity.spec.ts`, asserting `outbox` and `processed_events`
are defined identically across all four `DbContext`s (Orders, Fulfillment, Billing, Notifications)
— read from the live database in every case, never from EF metadata.

Both feature 9's blocking review defects (D1 — foreign keys silently missing and undisclosed; D2 —
a sequence counter widened to `bigint` against the spec) were treated as binding from the start,
exactly as feature 10 did: all three FKs are present in the first-generated migration, guarded by
a closed-set `ForeignKeyTests` I armed myself; `invoice_number_sequences.next_value` — **the third
and last of the three sequence tables D2 named** — is `int` from the entity's first version, with
a test asserting `int` and an arming probe proving the guard catches `bigint`.

## THE CROSS-CONTEXT PARITY TEST — this feature's distinctive deliverable

**File:** `tests/Billing.IntegrationTests/ReliabilityTableParityTests.cs`.

**How it compares.** The test migrates four *fresh* real MS-SQL databases on the shared
Testcontainers container — one per context (`OrdersDbContext`, `FulfillmentDbContext`,
`BillingDbContext`, `NotificationsDbContext`, the first two referenced as project references
only, never edited) — then reads `INFORMATION_SCHEMA.COLUMNS` (name, ordinal position, data
type, character max length, datetime precision, nullability) and the `sys.indexes` /
`sys.index_columns` catalogue (index name, uniqueness, ordered column list) directly from each
database. `Orders` is the reference context (the oldest, feature `db_orders`); every other
context's `outbox` (Fulfillment, Billing — Notifications has none) and `processed_events`
(Fulfillment, Billing, Notifications) shapes are compared against it. A divergence names **both**
sides explicitly, e.g. `outbox.event_type: character_maximum_length Orders=60 vs Billing=40` —
never a bare `Assert.Equal() Failure`.

`otc_notifications` is included in the `processed_events` half of the comparison and **explicitly
excluded, by name, from the `outbox` half** (the dictionary that builds outbox shapes only has
three entries: Orders, Fulfillment, Billing) — the task's instruction to say so rather than
silently exclude it. A second test,
`Notifications_Database_Contains_Only_ProcessedEvents`, independently confirms Notifications has
no `outbox` table at all (closed-set read of `INFORMATION_SCHEMA.TABLES`), so the absence is
proven, not merely assumed by omission from the comparison dictionary.

**How it was armed.** Changed `otc_billing.outbox.event_type` from `nvarchar(60)` to
`nvarchar(40)` in the Billing migration only (no Orders/Fulfillment file touched, respecting this
feature's scope restriction), forced rebuild, ran the named test:

```
outbox.event_type: character_maximum_length Orders=60 vs Billing=40
   at ReliabilityTableParityTests.Outbox_And_ProcessedEvents_Are_Defined_Identically_Across_All_Four_DbContexts()
```

**FAIL, naming both sides.** Restored from backup (`md5sum` verified identical to the pre-probe
copy, `grep` confirmed `nvarchar(60)` back in place), forced rebuild, re-confirmed: 22/22
`Billing.IntegrationTests` green.

Live cross-database confirmation (independent of the test, queried directly against the composed
stack) — `outbox` columns are byte-identical across `otc_orders`/`otc_fulfillment`/`otc_billing`
(12 columns each, same types, same lengths, same nullability), and `processed_events` is
byte-identical across all four databases (5 columns each). `diff` on the four raw
`INFORMATION_SCHEMA.COLUMNS` dumps is empty.

## What could not be done, and why

Nothing from the acceptance list was skipped. Not asserted, deliberately, matching prior features'
precedent: the `PK_*` clustered indexes and the EF-generated FK-supporting indexes
(`IX_invoice_items_invoice_id`, `IX_payments_invoice_id`) — neither is named by the Databases doc,
and both exist purely because EF gives every foreign key a supporting index by default (except
where EF recognised the spec composite index `IX_credit_items_credit_id_order_reference` already
leads with `credit_id` and reused it, same behaviour feature `db_orders`'s re-review documented
for `orders.retailer_id`).

The round-trip tests, like feature `db_fulfillment`'s, do not assert timestamp columns
(`CreatedAt`/`UpdatedAt`/`PaidAt`/`OccurredAt`) survive the read-back unchanged — only the
business fields are asserted. Feature `db_fulfillment`'s review (A1) flagged this as the same gap
in that feature and recorded it as a disclosed forward risk (`DateTimeKind.Unspecified` on
read-back from `datetime2`) rather than a defect; the same characterisation applies here and is
not repeated as new.

## Divergence list (complete and honest)

1. **`invoice_number_sequences.id` is `int`, not a UUID.** Same reasoning as
   `order_number_sequences.id`/`despatch_number_sequences.id`: §6 gives this table's `id` no
   type, only the implicit single-row-technical-counter convention from §3, and #7's own DDL uses
   `tinyint` there (`0002_invoice_sequences_and_order_uniqueness.sql`).
2. **`payload` (in `outbox`) is `nvarchar(max)`, not MySQL `json`.** MS-SQL 2022 has no native
   JSON column type; `nvarchar(max)` preserves insertion order (CLAUDE.md's wire-shape ruling,
   same as every prior database feature).
3. **No domain aggregates.** `Credit`, `Invoice`, `Payment` etc. are plain persistence POCOs, not
   the `BuyerCredit`/`Invoice` domain aggregates the Databases doc's prose describes — this
   feature is schema-only, matching `db_orders`/`db_fulfillment`'s precedent exactly.
4. **Non-spec-named indexes exist**: 2 genuinely-extra EF-generated single-column indexes on FK

## What surprised me

- **Divergence #6 above was the one place this feature improved on, rather than merely repeated,
  the established pattern.** Feature `db_fulfillment`'s review named the diagnostic-ordering issue
  as advisory-not-blocking and explicitly called out that it was "A2 from feature 9's re-review,
  copied through verbatim" — i.e. a defect that survives because a good file's shape gets copied
  along with its warts. Reordering the two assertions here (one line) was a small, free fix once
  noticed while the file was open, and it turned my own arming probe 1's failure message from
  "Expected: 3 / Actual: 2" (feature `db_fulfillment`'s shape) into
  "credit_items.credit_id: no foreign key found" — a genuinely more useful message for the next
  person who breaks this.
- **The self-inflicted false-success signal from running `quality.sh` concurrently with arming
  probes** (documented above) was worth catching before reporting a green run: the summary line
  said "all tests passed" while one project's 22 tests silently never executed. Discarding that
  run and re-running serially, rather than trusting the summary line, is exactly the "probe the
  claims, do not trust the summary" discipline `CLAUDE.md` and the reviewer role both ask for —
  applying it to my own run, not just the final report.
- **The parity test's design decision to compare against a single reference context (`Orders`)
  rather than all-pairs** turned out to be the right call for message clarity: an all-pairs
  comparison across four contexts would produce up to 6 redundant failure lines for one real
  divergence (Orders-vs-Fulfillment, Orders-vs-Billing, Fulfillment-vs-Billing, ... all disagreeing
  with whichever one changed); star-comparison against one reference produces exactly one failure
  line per actually-diverging context, which is what the arming probe's single clean failure line
  demonstrated.
