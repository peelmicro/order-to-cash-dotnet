## infra_compose (id 4, phase 4) — 2026-08-31

**Effort:** 1 session, ~1.25h wall-clock
**#7 baseline:** 1 session, ~4h (implementation ~1.5h, then two review rounds)
**Spec:** n/a (sdd: false)
**Tests:** no code yet. Verification was the running stack: 12 services healthy, the four databases created, the app login exercised in each, bootstrap idempotency re-run, and the healthcheck's failure mode probed directly

**What was built:**

`docker-compose.infra.yml` — 15 services (12 long-running, 2 one-shots, SonarQube behind a profile): MS-SQL Server, MongoDB, Kafka (KRaft), Redpanda Console, kafka-exporter, NATS core, Mailpit, OTel Collector, Jaeger, Prometheus, Grafana, n8n, plus `kafka-init` and `n8n-init`. `.env.example` scoped to what this phase actually creates, and a `.env` from it.

**Reused byte-identically from #7** (`cmp`-verified, nine files): the Kafka topic script and its Dockerfile, the OTel Collector config and Dockerfile, `prometheus.yml`, the Grafana dashboard JSON and both provisioning files, the n8n import script.

**Written here**: `infra/mssql/entrypoint.sh` and `infra/mssql/init/01-create-databases.sql`. The MySQL image runs anything in `/docker-entrypoint-initdb.d`; the MS-SQL image has **no init hook of any kind** — it execs `sqlservr` and nothing else. The entrypoint starts the engine in the background, waits until it answers a query, bootstraps through `sqlcmd`, then `wait`s so the container's lifetime and exit status remain the engine's. The init script is idempotent by construction, because unlike MySQL's once-only hook it re-runs on every container start.

**Deviations from the spec/plan:**

- **`COMPOSE_PROJECT_NAME=otcnet`**, decided at the human gate. #7 uses `otc`, so every container and volume except the database engine's would have collided name-for-name and #8 would have opened #7's Grafana database, MongoDB read model and Kafka log directory. Logical database names stay `otc_*` — that is shared-spec parity. Host ports unchanged, so the two stacks run one at a time.
- **MS-SQL pinned to `2022-CU26-ubuntu-22.04`**, matching how #7 pins every image. `2022-latest` shares a manifest digest with no specific CU tag, so it is genuinely unidentifiable.
- **Healthcheck `retries` cut 30 → 10** after measuring the real startup. See below.

**What the reuse saved — and what it did not:**

**Saved, and more than the ~1.25h vs ~4h suggests.** #7 spent two review rounds on this phase; almost every defect those rounds found arrived here as a comment in a file I copied — the Kafka `KAFKA_LOG_DIRS` mount mismatch (its D1), the init-script-must-be-`.sh`-to-read-env reasoning (D5), the healthcheck-passes-during-init trap, the kafka-exporter rationale, the topic-set-must-match-exactly assertion. The nine reused files needed no thought at all.

**Did not save: the MS-SQL bootstrap, which is the single largest piece of genuinely new infrastructure in #8.** No amount of #7 reuse helps when the engine has no initialisation mechanism to reuse *into*. That piece was written, debugged and probed from scratch and accounts for most of the 1.25h.

**Two plan predictions were wrong, both in #8's favour, both recorded rather than dropped:**

| | Predicted | Measured | #7 |
|---|---|---|---|
| Cold start to all-healthy | materially worse than #7 | **36 s** from empty volumes | 35–42 s |
| MS-SQL container RAM | 1.5–2 GB | **1.04 GiB** | MySQL ~400 MB |

Total infra footprint 2 492 MiB across 12 containers. The engine answers 4–9 s after container start; bootstrap adds ~3 s.

**Notes for #9:**

- PostgreSQL *does* have `/docker-entrypoint-initdb.d`, so #9 gets #7's mechanism back and should be quicker here than #8 was. Do not read #8's number as the cost of "porting infra" in general — it is the cost of one engine lacking one hook.
- Pin the exact image tag and check the digest. `2022-latest` matching no specific CU digest is the concrete argument.
- Make the database healthcheck assert the *databases exist*, not that the engine answers. Every engine accepts connections before your bootstrap has run.
- Set `retries` from a measured startup, not by copying another repo's shape.

**Effort:** 1 session, ~3h wall-clock — implementation ~1.25h, review round 1 ~0.75h (**REJECTED**), fix pass ~0.5h, re-review round 2 ~0.5h
**#7 baseline:** 1 session, ~3.5h — TS7 validation spike ~1h, scaffold ~1.5h, review ~1h; **approved on the first pass**
**Spec:** n/a (sdd: false) — contract was feature 6's 5-item `acceptance` array in `feature_list.json` plus CLAUDE.md's non-negotiables
**Tests:** 10 xUnit tests in `tests/Architecture.Tests`, all armed and proven to fail on a real violation — 6 `DomainPurityTests` (EF Core, Confluent.Kafka, NATS.*, MongoDB.*, ASP.NET Core, System.Text.Json), 1 `DomainDecimalTests`, 1 `SharedKernelHasNoPackagesTests`, 2 `DomainAssembliesTests` (non-vacuity). No `R<n>` mapping — pre-spec phase.

**What was built:**

`OrderToCash.sln` (classic `.sln`; .NET 10's `dotnet new sln` now defaults to `.slnx`) with nine projects: `SharedKernel` and `Contracts` (no layer folders, placeholders for features 7–8) plus seven services — Gateway, Orders, Fulfillment, Billing, Notifications, Projector, Seed — each with `Domain/`, `Application/`, `Infrastructure/`, `Presentation/` folders inside **one** `.csproj`, `RootNamespace`/`AssemblyName` = `OrderToCash.<Project>`. `Directory.Build.props` carries enforcement (`net10.0`, `Nullable`, `ImplicitUsings`, `LangVersion 14.0`, `TreatWarningsAsErrors`, `AnalysisLevel=latest`, `EnforceCodeStyleInBuild`) and `.editorconfig` keeps severities — no duplication, with a comment in each file stating the split. `Directory.Packages.props` pins every package centrally with transitive pinning on. `quality.sh` runs format-check → build → test → coverage collection, propagating the first failing exit code.

**Deviations from the spec/plan:**

- `Gateway` got a `Domain/` folder and is covered by the purity rules even though it is presentation-only in CLAUDE.md's layer diagram. Kept symmetric with the other six deliberately; inert until phase 13.
- **`quality.sh` collects and prints coverage but does not gate it**, with an explicit `TODO(feature 34 — sonarqube_quality_gates, phase 21)` at the point where the gate belongs. This is the deviation that matters: #7 discovered its own coverage gate had been inert for twenty phases, so a script that prints a percentage next to a green tick is exactly the failure mode this repository exists to avoid. Naming the owning feature in the file is the difference between a deferral and a silent omission.

**What the reuse saved — and what it did not:**

**Saved:** the ~1h TypeScript-7 validation spike that dominated #7's equivalent phase had no counterpart here — the .NET toolchain was already pinned and probed in phase 1, so there was no language-version gamble to resolve. The four-layer folder shape, the service list, the ports and the naming conventions were all inherited decisions that cost nothing to re-derive.

**Did not save — and this is the honest headline: #8 was NOT meaningfully faster than #7 on this feature (~3h vs ~3.5h), and it needed a rejection round that #7 did not.** Two reasons, both worth recording. First, the artefact itself is almost entirely stack-specific: #7's domain-purity guard was an ESLint `no-restricted-imports` rule scoped to the **path glob** `apps/*/src/domain/**`; #8's is NetArchTest over **namespaces**. Nothing ported. Second — and this is the interesting part — **the translation silently lost a property the original had for free.** A path glob covers subdirectories automatically; the first implementation's `ResideInNamespaceEndingWith(".Domain")` is a literal suffix match that covers `OrderToCash.Orders.Domain` but *not* `…Domain.ValueObjects`, `…Domain.Events` or `…Domain.Errors` — precisely where CLAUDE.md says aggregates, value objects and domain events live from feature 7 onward. The reviewer caught it by placing a live `MongoDB.Bson.ObjectId` and a `System.Text.Json.JsonSerializer` call in a nested domain namespace and watching **all six purity tests stay green**. The implementer's arming evidence had been honest and complete — it simply never tested the nested case, so a truthful report gave false confidence. Fixed with a single shared `DomainNamespacePattern = @"(^|\.)Domain(\.|$)"` constant consumed by both rule families, plus two non-vacuity tests guarding the assembly set; re-review armed all six rules at nested namespaces and both new tests.

So the reuse dividend on this feature was roughly zero, and it was consumed by a defect that only existed *because* of the port. That is a result, not a failure to record.

**Process evidence (kept deliberately, not smoothed over):**

This feature took an implementer pass, a rejection, a fix pass and a re-review. The implementer appended its correction rather than rewriting its report, so both the defect and its repair are in the record. This is the second consecutive phase to surface the same class of problem — `messaging_topology` (id 5) offered a `grep -c jetstream` check that returned 1 whether JetStream ran or not — but with one difference worth the ink: **that one was caught by the human at the gate; this one was caught by the reviewer agent.** The guard-that-does-not-guard is the dominant defect class in this build, and the harness is now catching it one layer earlier than it did last phase.

**Notes for #9:**

- **When porting a rule between stacks, port its *scope*, not just its *intent*.** A path glob, a namespace predicate and a package boundary are not interchangeable; ask explicitly which one the original relied on and whether the translation still holds. FastAPI will face this again — Python has no namespace/assembly split at all, so the domain-purity guard will likely be an import-graph or module-path check, closer to #7's glob than to #8's namespace match.
- **Arm every guard at the shape the code will actually take, not the shape it has today.** Placeholder types in flat namespaces are not representative of a real domain layer; the arming case must use the sub-namespace/sub-package structure the next feature will create.
- **Add a non-vacuity test for any rule that selects a type set.** A rule over an empty selection passes and looks green. Breaking the selector here left 7 of 10 tests passing — only the explicit non-vacuity test caught it. Budget one such test per selector-based rule from the start; it is far cheaper than discovering the gap twenty phases later.
- Do not fake a coverage gate to make the quality script look complete. Print the number, name the feature that will enforce it, and leave the TODO in the file.

### `seed_job` — addendum: the deferred #7 live-database comparison, now performed

The feature's acceptance carried a **row-count and checksum comparison against #7's seeded databases**, deferred at submission because it needs #7's MySQL container running and that was a decision for the human. Authorised and performed after the feature closed. Recorded here rather than reopening the feature, because it changes no code — it either confirms the parity claim or refutes it, and it confirms it.

**Method.** #7's `otc-mysql` started read-only alongside #8's stack (different port, 3306 vs 1433; #7's six volumes untouched, verified after). Master data extracted from both engines as ordered, colon-joined business columns — one row per line — and diffed **row for row**, then hashed as a whole.

**Result: 413 master-data rows, identical on both sides, same SHA-256 (`7602fe78…`).**

| Table | Rows | |
|---|---:|---|
| `currencies` | 3 | identical |
| `products` | 12 | identical |
| `retailers` | 7 | identical |
| `companies` | 22 | identical |
| `stock` | 215 | identical |
| `credits` | 154 | identical |

The six **seeded orders** also match field for field — reference, status, cancellation reason and all three money amounts, including `ORD-000006` as `cancelled` / `credit_rejected`, which is the one cancelled order the acceptance requires.

**Why the transactional counts differ, and why that is not a divergence.** #7's live database holds **1 390 orders**, 3 425 order items, 1 174 despatches and 1 170 payments. Those are not seed data: #7's stack ran for hours with the n8n order generator, and the seed contributed only the first six. Comparing raw table counts on those tables would have compared #8's seed against #7's seed **plus its entire demo history** — a meaningless number that would have looked alarming. The comparison is therefore scoped to master data plus the seeded-order subset, and that scoping is itself the finding: **a parity comparison against a database that has been *used* must isolate the seeded subset first, or it measures the wrong thing.** #9 will hit this too.

**Three flaws in my own comparison, each caught before it produced a false result** — worth recording because each would have yielded a confident, wrong answer:

1. **`STRING_AGG` without an explicit `nvarchar(max)` cast** truncated silently on the MS-SQL side, producing three *identical* hashes for three different tables. Three identical checksums is impossible for different data, and that tell is what exposed it.
2. **MySQL's `GROUP_CONCAT` truncates at 1 024 bytes by default** (`group_concat_max_len`). The #7-side hashes were being computed over truncated strings. Neither side warns.
3. **The MySQL client did not emit UTF-8**, so `Aldi España` came out as `Aldi Espa?a` and the first diff reported *three* tables differing. Those were my extraction's mangling, not the data's.

The fix for all three was to stop hashing aggregates and **dump rows to files and `diff` them** — transparent, per-row, and structurally incapable of silent truncation. A hash is a fine *summary* of a comparison you have already seen; it is a poor *substitute* for seeing it.

The difference between this feature and that one is the shape of what was inherited: feature 12 inherited **data** and no assertions over it, and was rejected; this feature inherited a **design with citations to the reference implementation's source**, and passed first time with one minor gap. **Notes for #9 (FastAPI):**

- **Write the design with citations to #7 by file and line, not by claim.** It is the single highest-leverage habit this feature demonstrates: it collapsed 16 gate open points to zero, and it makes the review a lookup rather than an argument. Where you cannot cite, you have found a genuine decision — take it to the gate and say why the citation was unavailable.
- **Table T-1 as a data table, not a switch cascade.** #7 recommended this and it holds in a third language: eleven edges as a frozen set of value-equal pairs makes the exhaustive 9 × 8 = 72-pair proof possible, makes terminality need no code at all (`completed` and `cancelled` simply never appear as a source), and makes the "the table equals the spec" test a set comparison in both directions. - **Arm the *suppression* direction, and on a different edge from the one the implementation report used.** Five of T-1's twelve edges must emit nothing, and a test that only checks the seven emitting edges will pass forever while a sixth fact leaks onto a closed catalogue. The probe is "add an emission and watch a named test fail", and it must be run on an edge nobody has armed before, or it proves only that one line of one method is guarded.
- **When you write a validation the reference implementation lacked, arm it in the same commit.** #8 correctly fixed #7's D3 currency hole in `Rehydrate` and left it guarded by nothing; deleting the whole check kept the suite green. Fixing an inherited defect without arming the fix produces code that is right today and unprotected tomorrow — and it will read as *more* trustworthy than the reference precisely because someone thought about it.
- **A constraint that appears only in an orchestration brief has no gate behind it.** Where it contradicts a ratified specification, the specification wins, and the right move on discovering the conflict is to stop and report rather than to pick a side silently. One round-trip is cheap; a feature that looks complete and is not is not.

### The four defects this feature shipped, and what each one cost

Every one of them **passed a green suite with a complete arming table beside it.** That is the single most transferable fact here.

1. **D1 — `IDispatcher` registered `AddSingleton`, capturing the DI root provider.** Every handler would have resolved outside the request scope: in Development, a first-dispatch throw the boot did not catch; in Production, **silent** — one captive `DbContext` shared by every request for the process lifetime. Found by building a standalone consumer of the real project and running it in both host configurations; reading the registration line alone looks like a lifetime preference. Cost: one round. Fixed to `AddScoped`, guarded by a test that dispatches through two `CreateAsyncScope()`s and asserts two distinct instances, built deliberately **without** `ValidateScopes` so it reproduces the silent mode rather than the loud one.
2. **D7 — the "no MediatR" guard did not guard.** It read `Assembly.GetReferencedAssemblies()`, and Roslyn only writes a reference-table entry for an assembly whose types the code *uses*. A real `PackageReference`, unused, left the suite green with `MediatR.dll` physically in the output. Its doc comment claimed it "cannot be defeated by any route a reference could arrive by". Found by installing an actual MediatR package, not by mutating a search string. **The distinction that matters:** `DomainMustNotDependOnCqrs` reads the same metadata and is *correctly* blind to a present-but-unused reference, because that rule forbids **depending**; acceptance item 4 forbids a **reference**, so metadata was the wrong source. Same technique, opposite verdicts, and the difference is what the rule is about.
3. **D8 — a fix that destroyed an analyzer guarantee.** D3's correct fix replaced a compile-time-checked `await handler.HandleAsync(@event, cancellationToken)` with `MethodInfo.Invoke(handler, [@event, cancellationToken])`. CA2016 — an **error** in this repository — cannot see through an `object[]`. The token could be silently dropped on every published fact with the suite green.
4. **D9 — a rule kept current everywhere except in the file that tells reviewers what to enforce.** After the `src/Cqrs` amendment, `.claude/agents/reviewer.md` still carried the superseded two-project rule. Worse than a stale injected cache: the next reviewer would have read it *from disk, exactly as instructed*, and rejected correct code with confirmation that it had checked.

**D7 and D8 share one shape, and it is the lesson:** each was a fix that solved the reported problem while quietly discarding a property the *old* mechanism provided for free — a grep that saw presence, a compiler that checked arguments. Neither loss is visible from inside the fix. The question that finds them is **"what did the old mechanism guarantee, and does the new one still guarantee it?"** — not "does the new one solve the reported bug?".

**One advisory carried:** D10 — the replacement project-file guard reads three hardcoded paths of twenty-one. It is closed for the realistic route (central package management forces `dotnet add package` through `Directory.Packages.props`, which is inspected — proven against `src/Orders/Orders.csproj`) and open to a hand-written `VersionOverride`, which is CPM-legal, restores cleanly and needs no central entry — proven, suite green. Non-blocking: acceptance item 4 requires a *state*, not a guard, and unlike item 3 does not say "proven by a test". Close it when the solution-wide equivalent lands in `tests/Architecture.Tests`, and **glob** the project files rather than listing them — a glob is what makes it closed; a list is what made this one a whitelist.

### What the reuse saved — and what it did not

**Nothing, by construction: there was nothing to reuse.** That is the point of the row.

**The cost question, answered on the evidence rather than chosen.** Both tempting write-ups are wrong.

*"Hand-rolling cost us dearly"* miscounts. Three of the four defects were not caused by hand-rolling the dispatcher — they were caused by hand-rolling the **guards**. D7 and D8 are defects in *tests written to satisfy review findings*; a framework would not have prevented them, because a framework would have had no such tests at all. D9 is an amendment-process defect. Only **D1** is a genuine hand-rolling bug — one `@nestjs/cqrs` would never have had, because DI lifetime was someone else's solved problem — and it was found and fixed inside one round.

*"Hand-rolling bought us guarantees"* undercounts the bill. The guarantees are real: boot-time validation of the whole handler graph, which `@nestjs/cqrs` does not offer, and a fourteenth architecture rule. But they cost three review rounds, and **two of those rounds found that the guards themselves were false** — the guarantee was claimed before it existed, twice.

**The measured statement: hand-rolling was roughly cost-neutral on the code and expensive on the proof, and the expense bought a verification surface the framework route does not offer at all.** The dispatcher was substantially right on the first pass — all four acceptance items passed in round 1 and never regressed; ~150 lines, ~3h. What took three rounds was *proving* it, against ~790 lines of test. That is not a hand-rolling cost, it is the arming protocol applied to code no one else has ever tested.

**The uncomfortable corollary, and it is the honest finding.** The reason a framework looks cheaper is that nobody probes a framework. D1's bug class — a service locator capturing the root provider — exists in framework-based systems too, unexamined, because there is no arming table pointed at someone else's package. #8 paid three rounds to learn that its own dispatcher was wrong in three ways; #7 paid nothing and knows nothing about `@nestjs/cqrs`'s equivalents. **That is not a benchmark result in #7's favour. It is a difference in what each assessment can claim to know**, and the Phase 24 table should say so in prose rather than resolve it to a number.

**Caveats, so the number is not over-read.** n = 1, one session, and the proof cost is inflated by this being the first feature to apply the arming protocol to a shared runtime project — there was no precedent to copy. The dispatcher is consumed at **zero marginal cost** by features 15 onward across all six services, so the amortisation is real and entirely unmeasured today. Re-read this entry after feature 20 before quoting its ratio anywhere.

**A parity trade-off recorded, not hidden:** the dispatcher is binding in all six services even though it does not fit all six equally — the Gateway's "commands" are outward NATS RPC, and Notifications and Projector are pure consumers where it adds a hop a direct call would not need. Accepted deliberately, because **#7 used `@nestjs/cqrs` in all six, and a #8 that used its dispatcher in three would turn an architecture difference into what looks like a language difference** in the per-feature numbers.

**Notes for #9:**

- **You will face this decision too, and your answer is probably different.** Python's ecosystem has no MediatR-equivalent licence problem, and FastAPI's `Depends` already does scoped resolution. If you adopt something, say what you did **not** learn as a result — that is the honest counterpart to this entry, and it is what makes the trilogy's three rows comparable as *knowledge*, not just as hours.
- **Whatever you build or adopt, probe the scope/lifetime boundary yourself, from outside.** Build a throwaway consumer, dispatch from two independent request scopes with a scoped dependency, and assert you got two instances. D1 passed a 96%-covered, fully-armed suite. **Line coverage is not scope coverage**, and a service locator hides its resolutions from every static check the platform offers.
- **Match the guard's source to the rule's wording.** "No X **reference**" lives in the dependency manifest; "no X **dependency**" lives in the compiled artifact. Reading the wrong one produces a guard that passes while the thing it forbids is physically present in the output directory.
- **When a fix changes *how* something is checked, ask what the old mechanism guaranteed.** Replacing a typed call with a dynamic one, or a text search with a metadata query, silently drops whatever the old form got for free from the compiler or the analyzer. Both of this feature's round-2 defects were exactly that, and neither was visible from inside the fix.
- **Arm against the real target, not the mechanism.** Substituting a search term to make an assertion fire proves the *reporting* path; it says nothing about the *detection* path. If the claim is dependency-graph-level ("this package is absent"), the probe must be dependency-graph-level (actually install it). No `sed` expression substitutes for that honestly — and `scripts/arm-probe.sh` will tell you when your mutation proves nothing, which is a different finding from "the guard does not guard".
- **When you amend a convention, sweep every rule-bearing file — agent definitions included — and leave behind a mechanical check that the old phrasing appears nowhere.** This project caught a stale rule in its reviewer's own instructions *one round after* catching a stale rule in its conventions file, under maximum attention. A habit that fails twice under maximum attention will not hold at phase 20.

**#7's baseline for the same feature: 1 spec session, 1 gate revision, 1 implementation session, 1 review pass — approved first time, ≈1 h 45 min implementation, ≈35 min review.** #7's own history calls it *"the cheapest `sdd: true` feature of phase 8 by a wide margin, on the most complex surface"*. #8 spent roughly **three times** #7's total on it. **This is a loss, it is recorded as one, and the reason is attached rather than explained away.**

### What the reuse bought, and what it could not

**The orchestrator itself was transcribed, and it was right on the first pass.** The fourteen-row step table, the compensation mapping, the precondition matrix, the redelivery semantics and the `R29` retry/dead-letter split all arrived from #7 as settled decisions with citations. The spec pass closed **20 of 22** open points from #7's own gate record rather than re-deriving them. **Across four review rounds, not one reviewer defect touched that code.**

**What could not be transcribed was the proof.** #7 got its commit contract from `kafkajs` and its dispatch contract from `@nestjs/cqrs` — ambient guarantees supplied by the framework, which its tests could assume rather than establish. #8 hand-rolls both against `Confluent.Kafka` and its own dispatcher, so every one of those guarantees is #8's to prove. **Every hour of the extra six went into test infrastructure, and every defect any reviewer found across four rounds was in test code:**

1. **Round 1 — D1 (blocking).** `SO9`'s "the committed offset advances **only after** a successful handler" was inferred from a redelivery instead of read from the broker. Flipping `EnableAutoCommit` to `false` — a change that makes every restart replay every fact on three topics, forever, silently — left the whole suite green. The repair reads the `orders.saga` group's committed offset via `IConsumer.Committed` on a throwaway consumer, with a `TaskCompletionSource` gate replacing a wall-clock guess; the first rewrite of it failed on *correct* code and was caught before review.
2. **Round 2 — D3 (blocking).** `R25_...` published `stock.reserved.v1` directly to Kafka without waiting for the relay-published `order.placed.v1` to have been consumed. Both facts share the `Placed` precondition, so whichever won decided the outcome and the test could go red on correct code. Fixed with a **state gate** — wait for the `stock.reserve` command to reach `sent`, which exists only because `order.placed.v1` was consumed — not a longer sleep.
3. **Round 3 — D4 (blocking) and D5 (required).** A *second*, independent unsynchronised gate in the same test: the redelivery loop waited on `(correlationId, marker)` while asserting on `(correlationId, eventType, marker)`, so from iteration 2 onward the wait was satisfied by an **earlier iteration's** row and gated nothing. Nine of ten iterations were unguarded on every run, and the only thing holding the test together was the incidental latency of an unrelated `SELECT`. D5: the fix round's arming table had credited that failure to D3.
4. **Round 4 — approved.** The wait now takes the event type and the wait predicate is **literally the assertion's predicate**, so the failure is removed by construction.

**The only production defect in the entire feature — the sweeper's double-claim no-op, where `DispatchAsync` re-claimed a row the sweeper had just claimed and silently did nothing — was found by the implementer's own arming, before any review.**

### The finding, in one sentence

**Reuse moves the residual risk from *"did we model it right"* to *"does our proof actually prove it"* — and a wrong proof is green.** A transcription is checkable by reading it against its source; a proof is not, because a test that proves nothing and a test that proves everything both pass. That is why this feature cost three times #7's figure while containing, by the reviewer's count, zero wrong lines of shipped logic. **#7's framework made the guarantees ambient; #8's stack makes them yours, and yours means you must prove them.**

### The process finding — attribution versus isolation, and it caught both roles

**Three times in this feature a red run in its own suite was closed by *attribution* — an explanation of why the failure was believed to be a known cause — rather than by *isolation*, loading the mutation that would confirm or refute that explanation.** Round 1's fix pass attributed an `R25_...` failure to memory pressure; it was D3. Round 2's fix pass attributed a differently-shaped `R25_...` failure to "the same D3 root cause" on the strength of 15 clean runs; it was D4, an independent defect D3's fix could never have touched. Both attributions were written by someone who had, minutes earlier, correctly diagnosed the *previous* defect — which is exactly what made each feel like confirmation rather than a second, unloaded hypothesis.

The implementer wrote the rule in round 3, in their own words, and it is the most transferable paragraph the feature produced: **before writing a sentence that explains a red run in your own suite, isolate the failing test and loop it under the mutation the *new* explanation implies — not the one already believed to be the cause.** A green re-run, however many times repeated, answers *"does this still happen sometimes"* and never answers *"is this the same cause as last time"*.

**And it bound the reviewer in the very same round.** Round 4 re-ran the reproduction vehicle that had failed 2-of-4 for the reviewer and 3-of-4 for the implementer hours earlier; with the fix in place it passed 4-of-4, which looked like clean confirmation. The **control leg** — the *unfixed* code through the same vehicle — also passed 4-of-4. The vehicle had simply gone quiet as machine load fell. **A pass/fail ratio on that race is not stable across a few hours on one machine, so no ratio — 1-in-12, 3-of-4 or 15/15 — could ever have armed it.** The answer was not a larger sample but a different question: with a deliberately unmatchable event type in the wait, the test's duration goes from 16 s to **3 m 37 s** (ten iterations each burning their full 20 s budget), which proves the per-iteration gate is real, deterministically, on one run, at any load. **When the probabilistic vehicle dies, change the question, not the sample size.**

### A credit the round count hides

**This review found a real defect in already-closed, already-committed feature 15**: `EfCoreOrderNumberAllocator`'s self-seeding branch does `IF NOT EXISTS … INSERT` with no lock hint and no duplicate-key handling, so two genuinely concurrent *first-ever* allocations against a never-seeded sequence table can both lose the race. Found by a test written for this feature's A11 debt, reproduced deterministically after two redesigns (a `Barrier`-based version **deadlocked** live and had to be killed), reported rather than fixed — it is feature 15's code — and filed as **backlog id 45**, with *"invert, don't delete"* written into its acceptance criteria so whoever fixes it does not silently delete the test that proves the bug. Four rounds is expensive; four rounds that also reach backwards into closed, committed work is not simply expensive.

### A harness lesson paid for in this feature, and now a convention

Round 3's review reformatted `feature_list.json` with a JSON round-trip, then undid it with `git checkout -- feature_list.json` — and the file was **uncommitted**, so the checkout discarded every uncommitted change including the leader's backlog entry for the allocator defect. `CLAUDE.md` now carries the rule: **no agent runs `git checkout --` on `feature_list.json`, ever; to undo an edit to it, re-edit it.** Two things make it worth a rule rather than care. The existing no-`git checkout` clause is justified by files being *untracked*, so a reader who has internalised it concludes it does not apply to a tracked file — when in fact it applies **more**, because that file is almost always dirty with other writers' work. And **`init.sh` cannot catch the damage**: a backlog with a feature missing is still a valid backlog, still has at most one `in_progress`, still satisfies SDD coherence. That is the third disguise of the guard-that-does-not-guard in this repository — a check that fires on nothing, a check run against the wrong artefact, and now a check whose invariants are all satisfied by an incorrect state.

### Notes for #9

- **Budget the proof, not the model.** When you inherit a settled design, the implementation is cheap and the *evidence* is not. Plan the test infrastructure — commit contracts, fact-ordering gates, broker-side reads — as first-class work with its own hours, or it will arrive as review rounds.
- **Synchronise on state, never on time.** Every defect in this feature's tests was a wait that did not prove what the next line read. The repair is always the same shape: find an observable row or offset that *exists only because* the thing you are waiting for happened, and wait for that. `stock.reserve`/`sent` proves `order.placed.v1` was consumed; a broker-committed offset proves a commit happened; a `(correlationId, eventType, marker)` row proves *that* fact was ignored.
- **Make the wait's predicate identical to the assertion's predicate.** D4 was a wait that was strictly weaker than the read it guarded, and it survived a full review round because the gap was invisible on a green run. If they are not the same predicate, write down why.
- **A helper's contract must warn where it is unsafe.** D4 existed because a `count > 0` wait was correct for its original single-fact caller and silently wrong for a loop. The fix that lasts is the doc-comment at the definition naming the trap, not only the corrected call site.
- **Run the control leg.** Before you report "N/N green with the fix", run the same vehicle **without** the fix in the same session. If it is also green, you have measured nothing.

### The three review probes, and the one that mattered

1. **The classifier, re-armed at finer grain than the implementer's own.** The implementer disabled the whole switch (`=> false`, 10 of 23 adapter tests red) — which proves the classifier is load-bearing but cannot distinguish a genuine per-code `[Theory]` from one shared assertion. 3. **The sweeper exclusion — the probe that found what no arming the implementer performed could have reached.** The integration test's last line is `Assert.DoesNotContain(due, …)`, a negative assertion in a database holding exactly one row: on its face it could pass because the sweep returned nothing for an unrelated reason. ### The judgement calls, both upheld

**The closed set.** Nine terminal codes, three transient — re-derived from `asyncapi.yaml:2839-2855` before reading #7, and identical to #7's `isTerminalRpcErrorCode` member for member. Each of the nine names a decision the responder's domain reached about *this* request, unchangeable by re-asking under the same idempotency key; each of the three names a condition a later attempt can genuinely resolve. `TIMEOUT` is caller-produced by the schema's own description and never reaches the branch, but is listed transient for completeness. The one code that is a judgement rather than a tautology is `NOT_FOUND` — a visibility race on an eventually-consistent responder could in principle make a retry productive — and it is not one here, because every saga command follows the fact that establishes its subject's state and both sides live in this repository.

**Failing open on an unknown code.** An `RpcError` code outside the closed set falls **transient**, where #7's TypeScript has a `never`-typed default that throws. Checked, not accepted: #7's dispatcher catch is *generic*, so an unrecognised code's thrown `Error` is retried there too — TS's exhaustiveness device is compile-time, and its runtime behaviour is transient. C#'s catch is *filtered*, so throwing would escape `DispatchClaimedAsync` past the lease with neither park nor reject. **The divergence is in mechanism only; the behaviour matches #7's.** And the default is right on its own merits: the two wrong answers are asymmetric. A wrongly-terminal command is unrecoverable by construction — nothing re-claims a `rejected` row and no operator redrive exists — while a wrongly-transient one is bounded waste on a row whose status, attempts and last error an operator can see. Decisively, **the transient side is the side feature 27 will hook for DLQ/alerting**, so the code nobody modelled lands in the branch that escalates and the business "no" lands in the branch that only logs. That is the correct assignment.

**What was fixed:** feature 15's self-seed was `IF NOT EXISTS (SELECT 1 ...) BEGIN INSERT ... END` — two engine-level operations, an unlocked read then a conditional write. Under `READ_COMMITTED_SNAPSHOT`, which is on for all four deployed databases and (since feature 14) for every Testcontainers database too, the read takes no lock at all, so two genuinely concurrent **first-ever** callers both see "not exists" as true and the loser gets a primary-key violation on `order_number_sequences`. It is now one atomic statement: `INSERT INTO ... SELECT 1, seed.next_value FROM (SELECT ISNULL(MAX(CAST(SUBSTRING(...) AS int)), 0) + 1 ...) AS seed WHERE NOT EXISTS (SELECT 1 FROM dbo.order_number_sequences WITH (UPDLOCK, HOLDLOCK) WHERE id = 1)`. The allocation path's own `WITH (UPDLOCK, ROWLOCK)` claim — feature 15's, correct, out of scope — is byte-identical.

### The proof moved down a layer, and that is the transferable part

**The fix's correctness is a claim about SQL Server's lock manager under RCSI, so the review tested SQL Server's lock manager under RCSI** rather than reasoning about it from the test suite's colour. Three probes, in a throwaway `READ_COMMITTED_SNAPSHOT ON` database on the same image compose runs:

1. With one session holding an uncommitted `INSERT` of the key, a plain `SELECT ... WHERE id = 1` returned **0 immediately** — served from the version store, no lock, exactly the mechanism the bug depended on. The same read `WITH (UPDLOCK, HOLDLOCK)` **blocked to `Msg 1222, Lock request time out period exceeded`**. That single pair is the whole argument, observed.
2. The shipped statement under a forced interleaving: **0 rows inserted, no error**. The same statement with the hint removed: **`Msg 2627`**. Change in kind, at the engine, with no C# involved.
3. Four concurrent sessions each running the shipped statement against an empty table: **one insert, three no-ops, no deadlock**. That is what `UPDLOCK` buys over a bare `HOLDLOCK`, and it is why the fix does not trade a duplicate-key error for a 1205.

**The C# arming was then re-run independently and held**: hint removed, `touch`, `dotnet build --no-incremental`, **the armed SQL confirmed present in the built assembly with `strings` before the runs**, three separate `dotnet test` invocations, three identical failures at the same line. Restore from backup, rebuild, `strings` again, 4/4 green. No `git checkout --` at any point.

### The implementer got the hard call right, and the hard call was about the test, not the code

**The obvious inversion was available and would have been accepted by a less careful review.** "Sixteen concurrent first-ever allocations all succeed" is deterministic once fixed and only *probabilistic* as a detector of breakage — and this repository has already paid for that distinction twice, at feature 16, where the same sixteen-caller vehicle went **6/6 green under CPU load** while the bug was present. The implementer wrote that test anyway, because the acceptance bullet names it literally, and then **explicitly declined to arm against it**, saying so in the test's own doc comment rather than only in its report. The guard it armed against instead drives two sessions and **polls `sys.dm_exec_requests` until it observes B blocked by A**, with a bounded wait and a loud failure if the interleaving never happens — the wait's predicate is the thing the assertion depends on, which is the exact repair feature 16 needed three review rounds to arrive at. **A lesson from a previous feature was applied, unprompted, before the review asked for it. That is the cheapest thing that happens in this repository and it should be recorded when it does.**

**The reviewer's own probe added a wrinkle worth keeping:** on an idle machine the sixteen-way test failed 3/3 armed too. It is a stronger detector today than its comment claims — and the comment should stay conservative anyway, because "today, idle" is not a property of a guard.

### The finding: three defects, one class, and a process that cannot see it

`order_number_allocator_seed_race` is the **third** instance in this build of **a property #7 got for free from its engine or its language being dropped when the *shape* of #7's code was carried across** — after JSON key ordering (MySQL's `json` column normalisation mistaken for a wire requirement) and money column widths (MySQL's `int` made safe by JavaScript numbers being doubles). Here, `INSERT ... ON DUPLICATE KEY UPDATE` is atomic *because the statement is the unit of atomicity*; `IF NOT EXISTS ... INSERT` reads like the same sentence and is two statements.

**All three shipped green, through a review, against passing tests, and all three were found by a later feature's review reaching backwards into closed, committed work.** That is the cost worth naming: not the fix (0.9 h here), but the re-opening — a backlog entry, a fresh briefing, a full review, and a hole in the effort record where the original feature's true cost belongs.

**Nothing in the current process would catch the fourth, and the reason is structural.** Traceability runs `R<n>` → test, and every one of the three satisfied its requirement text exactly ("allocate a unique sequential reference", "integer minor units", "camelCase, nulls omitted"). The arming protocol does not reach them either: arming proves a guard fires when a behaviour is **deleted**, and in all three the behaviour was present and correct on the single-caller path the guard exercised. **The process never asks what property of #7's version made it correct** — only whether #8 produces the same output on the paths anyone thought to test.

**Proposed, for the human gate rather than decided here:** one line per ported idiom in the implementer's report — *"#7 relied on X (atomicity / width / ordering / isolation); in #8 that property is supplied by Y"* — required wherever #8 renders a #7 statement in a different engine or language, with the rule that **when the property was engine-provided in #7 and must be hand-built in #8, it needs a guard test of its own.** It is a small mechanical addition to a document the implementer already writes, checkable by a reviewer in seconds, and it is the question that would have caught all three at the moment they were written.

### The `git checkout --` incident, and the second amendment it produced

**It happened again, one feature after the rule was written for it.** An implementer transitioned the backlog with `json.load`/`json.dump`, `ensure_ascii` defaulted to `True` and re-escaped every em-dash in the file, and the instinct to undo a mangled file reached for `git checkout -- feature_list.json` — which restored HEAD and briefly destroyed the leader's uncommitted state (feature 42 `done`, feature 46 added). It was **disclosed in full, unprompted**, under a heading naming it a mistake, with the mechanism, the collateral and the recovery route; the state was reconstructed and then verified **independently by the leader**, which matters, because the implementer's own three checks (valid JSON, three intended semantic changes, `init.sh` green) all pass on a file that is internally consistent and wrong.

**`CLAUDE.md`'s amendment moves the rule upstream to the trigger**, and that is why it is expected to work where the first version did not: *to undo an edit, re-edit it* is advice addressed to a moment that only exists after the damage, whereas *do not rewrite this file to change one value* is addressed to the action both incidents actually started with. Two refinements were recommended at review and are recorded here for whoever next touches that section: state the post-condition as **"the diff shows only the lines you intended"** rather than "one insertion and one deletion" (this session's own legitimate edit was 17/2, because it also added id 46, and a check that cries wolf on correct work stops being run); and accept that **prose was already proven insufficient** — the rule was in the offending agent's context when it broke it. The mechanical form is for `init.sh` to keep a snapshot of `feature_list.json` and warn when the live file has **lost** an id or a status the snapshot had. `CLAUDE.md` says `init.sh` cannot catch this; it cannot catch it *from the file alone*, but it can catch it from the file plus its own history, and both incidents would have surfaced within seconds.

### What round 2 added, and why the third mutation family is the finding

The fix was armed by the implementer with the two mutations the verdict named, and round 2 ran both independently — both fail, at **different line numbers**, which is what proves the two halves are pinned separately. Round 2 then ran a third mutation nobody had specified: **hoist both mints and pass them crossed** (`idB` as the advice id, `idA` as the fact's `eventId`). Nothing is deleted, nothing is externally minted, both ids still come from the delegate and both are still distinct — and the test still fails.

That probe is the generalisable part. This build already knows that **deleting the emission** and **corrupting a payload field** are two different families that find different defects (feature 17). This feature adds a third face of the second: **substituting the *source* of a value with something that produces an equally valid-looking value.** A deletion probe cannot see it (the field is present), and a corruption probe can only see it *if the test supplied the expected value* — which is exactly what `Assert.NotEqual` fails to do. The rule that follows is about the test's **inputs**, not its assertions: for any field whose value the test does not control — ids, clocks, generated references — the test must inject the source (a `newId` delegate, a fake clock) or bracket it, or the field is unguarded no matter how many probes are run against it. `despatchDate` in this same feature is the positive instance: round 1 found it asserted nowhere, and the fix brackets the RPC with `before`/`after` so that a corrupted clock value fails `Assert.InRange` — which round 2 confirmed by adding three minutes to it in the payload mapper.

The fix round added the `despatch.create` versus `stock.release` race the `R36` matrix row had always named and had until now realised only by argument, and reported it green over five independent runs. **Five green runs are evidence of nothing** — green is the expected outcome both when the guard is live and when the two requests never actually overlap. Two things about that test are worth carrying forward. It **caught a real error in its own first draft** — the author assumed the losing `stock.release` would answer F5's `already_released` no-op, and the running system answered `PRECONDITION_FAILED` because `StockItem.Release` refuses a *consumed* reservation as a terminal state (F4/FS10); the test was corrected to match the system rather than the reverse. And its "exactly one fact" check reads through a `WaitForAsync(rows.Count > 0)` before `Assert.Single`, which is safe here only because the despatch row and its outbox row commit together — **do not copy that shape into Billing**, where two facts can legitimately be written by two different commits.

### Notes for #9

- **Read every test's assertions back against its own name before submitting it.** The mismatch here was visible in twenty lines for the whole life of the feature and cost a review round. It is the cheapest check in this document.
- **An identity or provenance claim needs the test to supply the value.** If the expected value is not in the test, the assertion is about the shape of the output, not about where it came from — and no amount of arming will tell you otherwise, because the deletion probe kills it for the wrong reason and looks like success.
- **Arm the race, do not run it more times.** Repetition raises confidence in a signal you have not shown exists; one mutation of the mechanism the race is about (here: the lock hints) settles it in one run.
- **A delegate seam is only a property if every call site uses it.** Round 2 probed all four mint sites in `OrderStockReservation.cs`; before this feature exactly one was guarded, and after it four are. Count the sites when you add the seam.

### The confound that appeared this phase and will grow: the benchmark is partly measuring the harness

#7's review of feature 18 ran five hostile mutations and approved first pass. #8's ran six in round 1 and eight more in round 2, across **three** mutation families, and required every claim of absence to arrive as a command with its output. The round-1 rejection was for a test that #7's standard would very likely have passed — #7's own report for the same feature records N2, an asymmetry finding, as non-blocking prose. **So a measurable part of #8's 1.7× is a deliberately raised bar, not a slower language**, and the same is true of feature 17's third review round.

This did not matter much through Phase 8, when the harness was roughly #7's. It matters now: three convention amendments landed inside this phase alone (the ported-idiom ledger's first enforcement, the absence-as-command rule, and the two-mutation-families rule from feature 17), each of which *creates* review rounds by design. **Recommendation for Phase 10 onwards, and it costs one sentence per rejection:** record, for each rejection round, whether the defect would have been caught by #7's review standard. Without that field the final trilogy table will report harness maturity as a language penalty, and the one thing this repository exists to produce will be wrong in a way nobody can unpick afterwards.

### What the ported-idiom ledger actually bought, on the evidence rather than the hope

It was adopted at the Phase 8 gate with a 0-for-3 detection record behind it and the claim that *writing the line is most of the value*. Phase 9 is its first real test, and the honest reading is narrower than the hope:

- **It held up as an artefact.** Feature 17 authored twelve properties; feature 18 was the first feature to *extend* ledgered code rather than author it, and round 1 checked all twelve claims against what the new code does — **every one held**, including the two most likely to be assumed (the allocator's atomic seed and the outbox's per-row awaited insert). For a class with a 0-for-3 history, a ledger whose claims survive line-by-line checking is a real result.
- **Its value in this phase was as a review instrument, not as a prevention record.** The gap round 1 found (the un-hinted in-transaction re-read at `DespatchCreationService.cs:67`, correct only because RCSI makes the snapshot statement-scoped) was found *by walking the ledger's shape against new code* — the ledger did not contain the row. **You cannot observe a prevented defect**, so the ledger's central claim remains untested; what is observable is that it gave a reviewer a walkable structure and that structure found something.
- **It could not have caught this phase's actual translation defect.** Feature 46 — the fourth lost-in-translation defect — sits in code written *before* the ledger existed. That is honest rather than damning, but it means the ledger's protection begins now and covers nothing already shipped, which is precisely why it spawned backlog id 52 (the retroactive boundary sweep). **The ledger created that debt; it did not discharge it.**
- **The failure mode it has is legible: the row that mattered was the one nobody wrote.** A ledger built from recollection will always miss the boundary nobody thought about. Id 52's method — enumerate the value-crossing boundaries, then walk them — is the fix, and Phase 10 should derive Billing's ledger rows from an enumerated boundary list rather than from memory. That is the experiment worth running: four ported mechanisms, ledger rows written at spec time from an enumeration, and then a count of translation defects found afterwards. **If Billing ships without one, that is the first positive evidence the ledger prevents rather than merely documents.**

### A backlog that grew by six during a three-feature phase: working, or behind?

The phase opened with 46 backlog items and closes with 52; it closed exactly one entry (id 49, opportunistically, in about a minute). Both readings are available and the evidence favours a split answer.

**It is a process working, on three counts.** First, **provenance**: of the six new entries, ids 48, 51 and 52 are findings about work shipped in *earlier* phases and id 53 is two-thirds about earlier work — so the backlog grew mostly by **discovery**, not by production. Only ids 49 and 50 are defects this phase authored, and one of them was closed inside it. Second, **the instrument**: every one of the six was found by a mutation probe, an enumerating command or a ledger walk — none by prose review — and the enumerating-command rule adopted mid-phase found three sites in ten seconds that a careful prose sweep had reported clear minutes earlier. A backlog that grows because the detector got better is not the same thing as a backlog that grows because the work got worse. Third, **closability**: each entry carries concrete acceptance bullets and an arming clause, so none of them is a wish. Id 49's one-minute closure inside an adjacent feature is the proof of concept.

**It is also a process discovering it was behind, on one count that should not be softened.** Id 52 exists because a rule adopted at the Phase 8 gate cannot be applied retroactively to four services shipped before it, and id 51 exists because an instrument copied into three services carries a false sentence in three documents. Neither shrinks on its own, and **phases 10–13 port five more services from the same source** — so the discovery rate is about to be applied to a much larger surface while the closure rate stands at one per phase, achieved by luck of adjacency.

**The reading, then:** the number six is not the problem and suppressing it would be the worst possible response. The problem is that **five of the six are scheduled for Phase 10 by nothing stronger than a `phase` field**, and Phase 10 is a three-feature Billing phase that will also be the ledger's first prevention experiment. Either those five get real hours in the Phase 10 plan — ids 48, 50 and 53 are each one named test and are cheapest inside the features that already open those files (Billing copies the responder, so id 50 belongs there; Billing copies the payload tests, so ids 51 and 53 belong there) — or they slide to Phase 21 and become decoration. **The one thing that has been shown to work in this build is closing a backlog entry inside a feature that already has the file open**, and Phase 10's brief should say which entry attaches to which feature before the first implementer is dispatched.
