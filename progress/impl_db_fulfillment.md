# impl_db_fulfillment — feature 10, phase 6

## What was built

An EF Core 10 `DbContext` (`FulfillmentDbContext`) for `otc_fulfillment`, covering every table
in Databases doc §5: `stock`, `reservations`, `despatches`, `despatch_items`,
`despatch_number_sequences`, plus the reliability tables `outbox` and `processed_events` shared
verbatim with `otc_orders` (§4.3) — seven tables in total. One migration (`InitialCreate`)
creates all of them, plus every index the Databases document names.

This is schema-only, by design, matching feature `db_orders`'s pattern: the `StockItem` /
`DespatchAdvice` domain aggregates are out of scope here. The persistence types in
`Infrastructure/Persistence/Entities/` are plain POCOs (`Stock`, `Reservation`, `Despatch`,
`DespatchItem`, `DespatchNumberSequence`, `OutboxMessage`, `ProcessedEvent`), not domain
aggregates — there is no `Domain/` code in this feature, and none is reachable from
`Infrastructure/`, so `DomainPurityTests` (unmodified, in `tests/Architecture.Tests/`) passes
cleanly (12/12).

Feature `db_orders`'s two blocking review defects (D1 — 7 of 8 foreign keys silently missing and
undisclosed; D2 — a sequence counter's `next_value` widened to `bigint` against the spec, locked
in by a wrong test assertion) were read first and treated as binding lessons, not just
background: both foreign keys are present in the migration from the first generation (never
added in a fix pass), both are asserted by a dedicated `ForeignKeyTests`, and
`despatch_number_sequences.next_value` is `int` from the entity's first version, with a test
asserting `int` and an arming probe proving the guard actually catches `bigint`.

## Foreign keys — the exact set, with delete rules

#7's committed DDL for `otc_fulfillment`
(`apps/fulfillment/drizzle/0000_nappy_mad_thinker.sql:75-76`) emits exactly two foreign keys:

- `reservations.stock_id → stock.id`, `ON DELETE no action` (checked directly in the DDL, not
  assumed)
- `despatch_items.despatch_id → despatches.id`, `ON DELETE cascade` (checked directly)

Both are present in the migration from its first generation and asserted by
`ForeignKeyTests.Exactly_The_Two_Spec_ForeignKeys_Exist_With_The_Right_Reference_And_DeleteAction`,
which reads `sys.foreign_keys`/`sys.foreign_key_columns` on the real database (never EF's model)
and fails on both a missing FK and an *unexpected* extra one (closed-set assertion, same pattern
as feature `db_orders`'s post-fix `ForeignKeyTests`).

Live verification against the composed `otcnet-mssql`/`otc_fulfillment`:

```
parent_table     parent_column   ref_table   ref_column  delete_referential_action_desc
despatch_items   despatch_id     despatches  id          CASCADE
reservations     stock_id        stock       id          NO_ACTION
(2 rows affected)
```

Matches #7's DDL exactly.

## What could not be done, and why

Nothing from the acceptance list was skipped. Not asserted, deliberately, matching feature
`db_orders`'s precedent: the `PK_*` clustered indexes and the two EF-generated FK-supporting
indexes (`IX_reservations_stock_id`, `IX_despatch_items_despatch_id`) — neither is named by the
Databases doc, and both exist purely because EF gives every foreign key a supporting index by
default.

## Divergence list (complete and honest — this is the standard feature `db_orders`'s
rejected first submission did not meet, and its corrected report set)

1. **`despatch_number_sequences.id` is `int`, not a UUID.** Same reasoning as
   `order_number_sequences.id` in feature `db_orders`: §5 gives this table's `id` no type, only
   the implicit single-row-technical-counter convention from §3, and #7's own DDL uses `tinyint`
   there (also not a UUID).
2. **`payload` (in `outbox`) is `nvarchar(max)`, not MySQL `json`.** MS-SQL 2022 has no native
   JSON column type; `nvarchar(max)` preserves insertion order (CLAUDE.md's wire-shape ruling,
   same as feature `db_orders`).
3. **No domain aggregates.** `Stock`, `Reservation`, `Despatch`, `DespatchItem` are plain
   persistence POCOs, not the `StockItem`/`DespatchAdvice` domain aggregates the Databases doc's
   prose describes — this feature is schema-only, matching `db_orders`'s precedent exactly (the
   domain aggregates are a later feature, not yet scheduled by number at the time of writing).
4. **Non-spec-named indexes exist**: 2 EF-generated single-column indexes on the FK columns
   (`IX_reservations_stock_id`, `IX_despatch_items_despatch_id`), plus the `PK_*` clustered
   indexes. None requested by the Databases doc, none asserted, none conflicting with anything
   the doc names.
5. **The two FKs' delete rules were verified against #7's actual committed SQL file**
   (`0000_nappy_mad_thinker.sql:75-76`), not assumed from the general "only cascades where the
   parent-child relationship is exclusive ownership" pattern — the task explicitly warned the
   pattern from `otc_orders` (mostly `NO_ACTION`, one `CASCADE`) might not repeat identically
   here. It does repeat identically in this database (`NO_ACTION` for the `stock` reference,
   `CASCADE` for the `despatch_items → despatches` ownership relationship), but that was checked,
   not assumed.

Everything else — every table, every column type, every named index, every unique constraint,
both foreign keys — matches Databases doc §5/§4.3 and #7's DDL, verified against both a
disposable Testcontainers instance and the live composed `otc_fulfillment` database, not against
this project's own EF model.

## What surprised me

- **The two-FK count from the task brief was exactly right**, and matched #7's DDL byte for
  byte on the first migration generation — no fix-pass was needed here, because the lesson from
  feature `db_orders`'s rejection (write every documented FK explicitly, with no navigation
  property, `Restrict`/`Cascade` matched to #7's actual DDL rather than assumed) was applied from
  the start rather than discovered by review.
- **Copying `OutboxMessage`/`ProcessedEvent`/their configurations verbatim from Orders**, rather
  than re-deriving them from the Databases doc's §4.3 prose, was faster and also directly
  produces the byte-identical shape feature `db_billing`'s planned cross-context parity test
  needs — the task's explicit instruction to do this rather than re-derive turned out to matter
  more for correctness than for speed.
- **`despatches.order_reference` uniqueness comes from a *second* #7 migration**
  (`0002_despatch_number_sequence_and_order_reference_unique.sql`), not the initial one — #7
  added it later as a fix. Since #8 builds the final schema in one pass (same dividend feature
  `db_orders` recorded for `saga_commands`/`saga_ignored_facts`), this constraint is present from
  the start here rather than needing its own follow-up migration.
