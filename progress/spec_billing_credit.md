## Ported-idiom ledger — what was done differently, and why it matters for the experiment

Phase 9's closing assessment set the test explicitly: *"Phase 10 should derive Billing's ledger rows from an enumerated boundary list rather than from memory … If Billing ships without [a translation defect], that is the first positive evidence the ledger prevents rather than merely documents."*

`design.md` §15.1 enumerates **25 boundaries** — every inbound decode, every store read that decides something, every column write, every outbound encode, and the four process-level boundaries (concurrency, shutdown, transaction defaults, the in-process port hop) — **before** any of them was analysed. §15.2 has **one row per boundary, 25 rows**, including the six whose answer is *"nothing special is required here, and this is why"* (`L1`, `L9`, `L17`, `L20`, `L23` in part, `L25`).

Three rows exist **only** because the enumeration forced them and would not have been written from recollection:

- **`L11`** — the `datetime2(3)` instant round trip. Fulfillment's ledger has no such row because `ReservationSnapshot` carries no date; `CreditLedgerEntry.EntryDate` is the first one that does. #7's counterpart property came from a single `timezone: 'Z'` clause in a pool config.
- **`L7`** — the committed-exposure `Σ`. The obvious EF Core rendering, `db.CreditItems.Where(...).SumAsync(...)`, **drops the table hint**, so the one read the whole invariant rests on would be an unlocked snapshot read that looks completely ordinary in review. This is `L1`'s shape from Fulfillment applied to a *different statement form*, which is exactly the kind of second instance backlog id 52 records as going unported.
- **`L12`** — the `type` column token. A silently-skipped ledger row would move `Σ` and present as a wrong credit limit, not as a parse error.

Two rows were written and then deliberately answered *"nothing"*: **`L1`** (the bare-JSON wire, a real saving, since #8 has no packet layer and therefore no third copy of #7's serializer pair) and **`L17`** (no upsert is rendered anywhere, stated because feature 45's defect was exactly a check-then-act rendering of that idiom).

## Gate ruling (2026-09-05) — BOTH ROWS OVERRULED

The human ruled **NO to both recommendations**, with a standing instruction attached: **stop leaving issues to the next phase — fix them.**

That instruction is broader than these two rows and is recorded here as binding on the rest of this build, not just on this feature.

**Row 1 — OVERRULED. The `OB1` relay-parity family stays at seven files; make them identical.** The spec's recommendation was to narrow the set to five and exclude `OutboxWriter.cs` and `KafkaOptions.cs` on the grounds that making them identical needs a per-service `IFactPayloadMapper` port and a neutral base-event name — *"a redesign of two shipped services in service of a guard"*. The ruling is that the redesign is the work, not a reason to avoid it. Concretely this feature must: introduce the per-service payload-mapper port, give the domain-event base a neutral name usable by all three services, bring `src/Orders/` and `src/Fulfillment/`'s `OutboxWriter.cs` onto that shape, and unify `KafkaOptions.cs`. `BC17` keeps #7's obligation at its full scope, which is what reusing the id claimed in the first place.

**Row 2 — OVERRULED. Guard the overflow; do not accept "stated, not guarded".** The spec argued the sum is bounded by construction and that a guard would need a ledger the aggregate refuses to reconstitute. The ruling is that an unguarded money arithmetic path is not acceptable on the strength of an argument, particularly here: **#8 has already shipped one money-width defect that satisfied its requirement text exactly**, and the sentence that preceded it was the same shape as this row's own reasoning. The spec's own gate row says so, then recommends accepting it anyway — that is the tell.

The obstacle the spec identified is real but narrower than stated: `Reconstitute`'s refusal blocks one route to an overflowing ledger, not the arithmetic itself. Two guards are available and both are testable without fabricating a state the aggregate rejects: make the summation arithmetic `checked` so a wrap raises rather than wraps silently, and unit-test the summation function directly with values that overflow it. `Reconstitute`'s refusal stays as the outer bound and keeps its own arming (`tasks.md` B10) — but it is now the second line, not the only one.

**Status: `spec_ready` — revision required before `in_progress`.** The spec is sent back for a post-gate revision pass covering both rulings, as #7 did at its own feature 16 gate.

### Ruling 1 — the `OB1` parity family stays at seven files

`requirements.md` §1.7's boxed note is replaced: #8 guards **seven** files, not five, and the note now says so, names the gate that ruled it, and points at the specification of the work rather than at a justification for avoiding it. `BC17`'s requirement text is unchanged — it always claimed the family, and that is the point the ruling made.

**One property had to be re-supplied, and finding it is the reason the ledger exists.** `KafkaOptions.cs` was excluded from #7's parity family *because* it held the per-service client id; unifying it takes that home away, and an empty `ClientId` does not fail — librdkafka substitutes its own default `rdkafka`, so two services would share a producer identity silently. The canonical property is therefore `required` with no default, each service's own options class supplies the value, and omission is a `CS9035` **build** error. New requirement **`BC29`**; new ledger row **`L26`** at boundary B20; armed in `tasks.md` A8 by deleting the initialiser and recording the compiler's message verbatim.

**A second new ledger row, `L27` at B16**, states the thing the first pass got wrong in one line: #7's `outbox-recorder.ts` served every service because TypeScript is **structurally** typed. C# is nominally typed, so the same one-implementation property has to be constructed — a neutral base name and a port. ### Ruling 2 — guard the overflow

`design.md` §3.3's *"Arithmetic width"* paragraph is replaced by **three lines, in order of distance from the caller**: (1) `CreditExposure.Summarise` accumulates inside an explicit `checked` region and raises `CreditLedgerOverflowError`; (2) `Money.Add`/`Subtract`/`Multiply` become `checked`; (3) `Reconstitute`'s refusal is the **outer bound**, explicitly the second line and no longer the only one. New requirement **`BC30`**; new domain error `CreditLedgerOverflowError` (`CREDIT_LEDGER_OVERFLOW`) in §3.5 and §4.5, mapped **terminal** — a ledger that overflows will overflow on every retry, so a retryable code would spin the saga forever.

Two details are specified rather than left to the implementer, both because they are where the guard would quietly become decorative. The accumulation is written as **explicit loops, not `Enumerable.Sum`**: `Sum(IEnumerable<long>)` happens to throw in the current BCL, nothing in its signature says so, and *"the library did it"* is the answer this repository's ledger exists to refuse. And `checked` does not propagate into called methods, so the region must contain the arithmetic — which it does, because `Summarise` is the only place `BC5` and `BC6` are computed.

## The finding that came out of obeying ruling 1 rather than deferring it

Unifying `KafkaOptions.cs` **removed a property**, and the reason it existed is the point: **#7 excluded that file from its own parity family precisely because it held the per-service client id.** An empty `ClientId` does not fail — librdkafka silently substitutes `rdkafka`, so every service would have reported to the broker under the same name and the loss would have surfaced as ambiguous broker-side metrics rather than as an error.

Re-supplied as `required string ClientId` with no default, armed by recording the compiler error a missing initialiser produces. New requirement `BC29`, new ledger rows `L26` and `L27`.

**This is the argument for the gate's ruling, produced by the work itself.** The first pass's recommendation was to exclude the file and record the divergence; had that been accepted, the property would have been lost silently and the ledger row that catches it would never have been written — because nobody writes a ledger row for a file they have excluded from the family.
