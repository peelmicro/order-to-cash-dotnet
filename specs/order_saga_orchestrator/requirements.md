### 1.1 The `R29` split needs no shared amendment in #8 — it was inherited

#7 amended `specs/shared/test-matrix.md`'s `R29` row at its own gate (its open point 2), splitting one named test into two: the retry clause (`orders/integration/saga-command-retry.spec`) and the dead-letter clause (`orders/integration/saga-command-dead-letter.spec`, deferred to `observability_reliability`). **#8 inherited the amended row.** Verified mechanically for this spec pass: columns 1–4 of every row of §3 of #8's `test-matrix.md` are byte-identical to #7's; the only differences are column 5 (`TODO` here, #7's realisation record there), which is exactly what "reused verbatim" means for that file.

So no edit to `specs/shared/` is proposed by this feature, and none is needed. At close-out the implementer flips **column 5 only**, for the rows this feature actually makes green.

### 1.2 `R16` is not this feature's, and the interim behaviour is SO5

`R16` (consumer retry → `<topic>.dlq` → acknowledge) was deferred to feature 27 at feature 14's gate, and that deferral is recorded in `specs/outbox_and_idempotency/requirements.md` §1.2. This feature builds the first fact-stream consumer in the repository and therefore builds the first thing `R16` could wrap — but it does **not** claim `R16`, and it does not build half of feature 27's acceptance surface. What it builds instead is SO5: an exhausted command **parks durably and keeps retrying on a capped schedule, indefinitely**, which is observable in one `SELECT` and self-recovers the moment a responder appears. Feature 27 attaches the DLQ publication and the timeline entry to the park transition; the seams are written down in `design.md` §6.5.

## 2. Local requirements — `SO<n>`

These are genuine gaps: things `R19` – `R29` presume but do not pin down, which this assessment must make testable. None contradicts a shared requirement.

**`SO1` – `SO8` reuse #7's local ids deliberately**, as an explicit claim that #8 carries the same obligation #7 carried under that id. Where the .NET mechanism differs, the requirement says so. **`SO9` – `SO11` are new to #8**, and each names the reason #7 could not have faced it.

**SO1.** WHEN the orchestrator starts with no committed offsets for its consumer group, THE SYSTEM SHALL consume each of the three fact topics from the earliest offset, so that facts published before the orchestrator first existed are processed rather than skipped.

**SO2.** WHEN the orchestrator receives one of the facts it produces itself (`order.confirmed.v1`, `order.completed.v1`, `order.cancelled.v1`, `order.saga_failed.v1`), THE SYSTEM SHALL acknowledge it without dispatching any command, without opening a transaction, without writing a `processed_events` record and without loading any aggregate (`saga.md` §5: consuming them would be a loop).

> **The #8 delta in SO2 is the fourth fact.** #7's step table had thirteen rows and three skips because `order.saga_failed.v1` did not exist yet — #7 minted it in its feature 27. #8's `src/Contracts/Facts/FactCatalog.cs` already carries all **fourteen**, so #8's table has fourteen rows and **four** skips. `saga.md` §5's consumption map is the authority and it already shows `order.saga_failed.v1` as consumed by the projector alone.

**SO3.** WHEN a saga step both changes the order status and owes a follow-up command, THE SYSTEM SHALL commit the status change, the `processed_events` record, the `outbox` records and a durable **pending-command record** in one transaction, and SHALL issue the command only after that transaction has committed; IF the process crashes between the commit and the command issue — including before the in-process event-to-signal hop has run — THEN THE SYSTEM SHALL issue the command from the pending-command record on a later sweep, without re-consuming the fact; the durable pending-command record, **not** the in-process hop, is the delivery guarantee.

**SO4.** WHEN a command issued over the RPC transport times out or returns a transport error, THE SYSTEM SHALL retry it in line at most `MaxAttempts` times (default **3**) with exponential backoff starting at `BackoffMs` (default **500 ms**, doubling), each attempt bounded by `TimeoutMs` (default **5 000 ms**), while leaving the order status unchanged — refining `R29`'s "configured maximum" with this assessment's concrete policy.

**SO5.** IF the in-line attempts of SO4 are exhausted, THEN THE SYSTEM SHALL mark the command **parked** — durably, with the accumulated attempt count, the last error and the next retry time — SHALL log a structured saga-failure entry carrying the `correlationId`, and SHALL leave the order in its last legal status; WHILE a command is parked, THE SYSTEM SHALL re-attempt it on a sweep interval with capped exponential backoff, indefinitely, so that the saga resumes without operator action once the responder becomes available. *(Interim stand-in for `R29`'s dead-letter clause until feature 27 — see `design.md` §6.4, §6.5.)*

**SO6.** WHEN a command reply reports a **business rejection** (`outcome: rejected` from `stock.reserve` or `credit.hold`), THE SYSTEM SHALL mark the command sent, SHALL NOT retry it, SHALL change no aggregate state, and SHALL await the corresponding rejection **fact** to take the compensation path (`saga.md` §2: a command's response never advances the saga; §7: a rejection is a domain outcome, not a failure).

**SO7.** WHEN `stock.released.v1` is received for an order in status `stock_reserved`, THE SYSTEM SHALL map the fact's `reason` to the cancellation reason (`credit_rejected` → `CreditRejected`, `order_cancelled` → `OperatorCancelled`) and SHALL pass a `compensationSteps` collection built from the observed compensating fact (`Step = StockReleased`, its `eventId`, `eventType`, `occurredAt`) into `Order.Cancel`, so the unwinding is auditable in the emitted `order.cancelled.v1` (`R28`; the aggregate never observes the compensating fact — the orchestrator supplies it).

**SO8.** IF a consumed fact's `correlationId` matches no order in the write model, THEN THE SYSTEM SHALL record the fact as ignored with an `unknown_order` marker, SHALL acknowledge it, and SHALL NOT throw — a fact can never legitimately precede its own order's row, because `order.placed.v1` commits with the order in one transaction before it is published (`R13`), so an unknown order is cross-environment residue, not an ordering problem.

**SO9.** WHILE consuming the fact stream, THE SYSTEM SHALL advance the committed offset for a partition only **after** the handler for the message at that offset has returned successfully; IF the handler throws, THEN THE SYSTEM SHALL leave the committed offset unchanged so the message is redelivered, and SHALL NOT acknowledge it by any other means.

> **New to #8, and it inverts #7's task.** #7's equivalent open point (its row 5) was to **verify** that its framework's throw-implies-no-commit behaviour held. In `Confluent.Kafka` the default behaviour is the *opposite*: `EnableAutoOffsetStore` defaults to `true`, so the offset of a message is stored the moment `Consume()` returns it and is committed by a background thread every `AutoCommitIntervalMs` (default 5 000 ms) **whether or not the handler succeeded**. At-least-once therefore has to be **constructed** here, not confirmed. `design.md` §3.3 specifies the construction; the defaults quoted are from the `Confluent.Kafka` 2.15.0 XML documentation shipped in the package on disk.

**SO10.** WHILE a saga command is being issued or retried over the RPC transport, THE SYSTEM SHALL NOT occupy the fact-stream consume loop, so that a command whose responder is absent delays neither the consumption of unrelated facts nor the consumer group's liveness.

> **New to #8 because the mechanism #7 relied on does not exist here.** #7 got this for free from an RxJS stream subscription, which is inherently off the consumer's await chain. .NET's in-process dispatcher is a direct `await`, so the same composition written naively would put SO4's ~16.5 s worst case **on** the consume loop — and with no Fulfillment or Billing responder in existence (phase 9 and 10), that is the *normal* case, not the exceptional one. `design.md` §5.5 specifies what plays the role instead.

**SO11.** WHILE a saga command row is being dispatched, THE SYSTEM SHALL exclude it from any concurrent claim for a bounded lease; IF the dispatching process dies mid-attempt, THEN THE SYSTEM SHALL make the row claimable again once the lease has elapsed, so no command is stranded by a crash and none is dispatched twice concurrently by this process.

> **New to #8 as a written requirement**, because #7's claim was a single MySQL clause (`FOR UPDATE SKIP LOCKED`) inside a transaction it did not hold across the dispatch, and it left the lease implicit. MS-SQL has no `SKIP LOCKED`; #8 already established `WITH (UPDLOCK, READPAST, ROWLOCK)` as the equivalent and **measured** that it skips rather than blocks (`progress/history.md`, feature 14). Because the RPC issue happens outside the claiming transaction, the exclusion has to outlive that transaction — hence a lease, expressed entirely in columns the table already has. `design.md` §6.3.
