## 2. The incident this grounds in — and why #8's shape is not #7's

#7's `R16` work was grounded in a live Phase-12 incident: a fact whose `correlationId` was syntactically present but not a UUID passed its envelope-shape guard, threw deep inside the handler, and halted the Orders saga consumer **permanently** because the offset was never committed.

**That exact shape cannot occur in #8, and a test that reproduced it would be vacuous.** `Envelope<TPayload>.CorrelationId` is a `Guid` (`src/Contracts/Envelopes/Envelope.cs`), so a non-UUID `correlationId` fails `JsonSerializer.Deserialize` inside `SagaFactsConsumer.HandleMessageAsync`'s own `try`, and is already logged-and-acknowledged (`src/Orders/Presentation/SagaFactsConsumer.cs:70-88`).

**The failure mode itself is present, unguarded, in all three consumers, in a different shape.** In `SagaFactsConsumer`, `ProjectorFactsConsumer` and `NotificationFactsConsumer` the **payload** deserialisation sits *outside* the envelope `try` and throws `JsonException` on a structurally valid envelope whose payload does not fit its declared type; so does everything downstream of it — the dispatcher, the handler, the aggregate, the store. Any of those throws propagates out of `HandleMessageAsync`, out of `KafkaFactStreamSubscriber.ConsumeAsync` **before `StoreOffset`**, into the consumer's own `ExecuteAsync` catch, which logs, waits 2 s, re-subscribes from the last committed offset and redelivers the identical message — forever, on that partition. That is `R16`'s failure shape exactly, and it is the shape every `OR1` test below must reproduce.

## 3. Local requirements — `OR<n>` (Half A)

**OR1.** WHEN a fact consumed by `orders.saga`, `projector` or `notifications` — the three registered `ConsumerName` tokens — causes its processing to throw **after** the envelope-shape guard has passed, THE SYSTEM SHALL retry that processing in line up to a configured maximum number of attempts (`FACT_RETRY_MAX_ATTEMPTS`, default `3`) with exponential backoff (`FACT_RETRY_BACKOFF_MS`, default `500` ms, doubling), and on exhausting them SHALL publish the **unmodified original envelope bytes** to `<source-topic>.dlq` carrying `x-failed-consumer`, `x-attempts`, `x-error`, `x-original-topic`, `x-first-failed-at`, `x-failed-at`, `x-event-type` and the current `traceparent` (`asyncapi.yaml` `DeadLetterHeaders`), and SHALL then return normally so the consumer stores and commits the offset and the partition is not blocked. *(Refines `R16`'s "configured maximum" with this assessment's concrete policy, exactly as `SO4` already refines `R29`'s retry clause.)*

**OR2.** THE SYSTEM SHALL realise `OR1`'s retry-then-dead-letter wrapper as **one canonical file copied verbatim** into every fact-consuming service, parity-guarded by the same byte-identity-after-banner mechanism `IdempotentConsumer` already uses (`OI12`, `tests/Orders.UnitTests/IdempotentConsumerParityTests.cs`) — never as three independently written retry loops — and the guard SHALL require the copy from **every** service that owns a fact consumer and from no other.

**OR3.** WHEN a `saga_commands` row transitions into `parked` for the **first** time for that row, THE SYSTEM SHALL, in addition to the existing park bookkeeping (`SO5`, unchanged): (a) append exactly one `order.saga_failed.v1` fact for that order through the existing outbox, carrying the failed `command`, the accumulated attempt count and the last error; and (b) publish the row's triggering fact envelope to its source topic's `.dlq` with `DeadLetterHeaders` naming the saga's own consumer identity. THE SYSTEM SHALL perform (a) and (b) **at most once per row** — a later sweep cycle that re-parks the same row emits neither again — and SHALL NOT alter `SO5`'s indefinite capped-backoff retry of the underlying command in any way.

**OR4.** WHEN a message is published on the RPC transport or on the fact stream, THE SYSTEM SHALL inject the current W3C `traceparent` (and `tracestate` when set) into that message's headers; and WHEN such a message is received, THE SYSTEM SHALL extract that context and **continue** the trace — same trace id, a fresh span id whose parent is the injected span — rather than starting a new one. WHERE no span is active at publication time, THE SYSTEM SHALL emit **no** `traceparent` header at all rather than fabricate one. *(Refines `R57` with the concrete header names `asyncapi.yaml`'s `FactHeaders`/`RpcHeaders`/`DeadLetterHeaders` already reserve, and with the `outbox.trace_parent` column `outbox_and_idempotency` provisioned nullable and unused for this feature.)*

**OR5.** THE SYSTEM SHALL export every span and every metric over OTLP to the already-provisioned OpenTelemetry Collector, SHALL expose **no** per-service Prometheus-format scrape endpoint, and SHALL distinguish services by the OTel `service.name` resource attribute rather than by scrape target. *(Refines `R59`'s "expose metrics" with the mechanism `infra/otel-collector/otel-collector-config.yaml` and `infra/prometheus/prometheus.yml` were already built for. Both files are inherited from #7 in their post-decision state and this feature changes neither.)*

**OR6.** THE SYSTEM SHALL serve `GET /health/live` and `GET /health/ready` over HTTP on **every** service, each answering `openapi.yaml`'s `HealthResponse` schema, each service's readiness consulting exactly the dependencies it actually has, and every individual dependency probe SHALL be a real reachability call bounded by an explicit timeout — never a cached value, never an unbounded wait. *(Refines `R60` with the transport and the per-service dependency sets. The explicit-timeout clause exists because #7 shipped one probe without one and disclosed it: `order-to-cash-nestjs/progress/review_observability_reliability.md`, finding 1.)*

**OR7.** THE SYSTEM SHALL emit every application log record as a **single-line JSON object** carrying the trace id, the span id and — on every record produced while handling an inbound HTTP request, an RPC request, a consumed fact, a saga command dispatch or an outbox relay cycle — that unit of work's own `correlationId`; and WHERE no span is active, THE SYSTEM SHALL omit the trace fields entirely rather than render them as an empty or literal `"undefined"` value. *(Refines `R58`'s "structured log records" and its "every line" clause with this assessment's rendering. The omit-rather-than-render clause is #7's, ported: `apps/orders/src/presentation/saga-facts-log-trace-id.spec.ts:71`.)*

## 4. Local requirements — `RI<n>` (Half B)

**RI1.** THE SYSTEM SHALL persist, for every accepted `orders.create` request that supplies a `requestId`, that `requestId` against the created order under a uniqueness constraint that admits **at most one** order per `requestId` and **any number** of orders that supply none.

**RI2.** WHEN `orders.create` is received carrying a `requestId` for which a committed order already exists, THE SYSTEM SHALL perform no reference-data resolution, no stock check and no write, and SHALL return that order's original reply. *(An optimisation over `R62`'s correctness requirement, not a substitute for `RI3`.)*

**RI3.** WHERE two `orders.create` requests carrying the same, not-yet-committed `requestId` are processed concurrently, THE SYSTEM SHALL let exactly one of them commit an order, SHALL cause the other to detect `RI1`'s uniqueness violation — distinguished from a violation of any other unique index on the same table — rather than commit a second order, and SHALL then resolve that request to the winning order's reply by re-reading it, never to an error and never to a second order.

**RI4.** WHERE `requestId` is omitted from `orders.create`, THE SYSTEM SHALL place a normal order, performing no lookup against `RI1`'s constraint and no deduplication.

**RI5.** WHERE `orders.create` supplies a `requestId`, THE SYSTEM SHALL use it as the `causationId` of the resulting `order.placed.v1`, so the causal chain is reconstructible from the client's own key; WHERE it is omitted, THE SYSTEM SHALL mint a fresh causation id as today. *(Ported behaviour, not a new invention: #7's `apps/orders/src/application/place-order.handler.ts:143` and `:205-211`. #8 currently mints a fresh id unconditionally — `src/Orders/Application/Commands/PlaceOrderCommandHandler.cs:88`. Recorded as a local requirement rather than smuggled into `RI1`'s task because it changes already-shipped, approved behaviour and must be visible at the gate.)*

## 6. What is deliberately NOT in this feature

- **The composed-stack observation of `R56`.** This feature proves the **mechanism** — every hop injects, every hop continues — per hop, against an in-memory span exporter. Standing up all six services plus a real Jaeger and *observing* one continuous trace is `saga_e2e_verification` (feature 28). The split is `test-matrix.md`'s own `R56` row, inherited from #7's gate, not narrowed here.
- **Dashboards.** `observability_dashboards` (phase 22) builds Grafana content; this feature makes the data exist. `infra/prometheus/prometheus.yml` and `infra/otel-collector/otel-collector-config.yaml` are already in their post-decision state and are **not edited**.
- **Any change to `SO1`–`SO11`, the step table, or the sweeper's retry policy.** Only the *first-park hook* is new.
- **A redrive consumer.** `asyncapi.yaml` is explicit that no service consumes a `.dlq` topic; redriving is a human act through the broker console.
