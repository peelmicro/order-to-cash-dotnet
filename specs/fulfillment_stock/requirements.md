# `fulfillment_stock` — Requirements (assessment #8, .NET)

> **The normative requirements for this feature are `R30` – `R36` and `R61` in [`specs/shared/requirements.md`](../shared/requirements.md) §4**, elaborated by [`specs/shared/domain-model.md`](../shared/domain-model.md) §4 (the `StockItem` aggregate, the `Reservation` child entity, invariants **F1** – **F5**, the lifecycle §4.2), [`specs/shared/saga.md`](../shared/saga.md) §2 (the command vocabulary and its idempotency keys), §4.1 (*"the race is real and intentional"*), §6 layer 3 (idempotent responders) and [`specs/shared/asyncapi.yaml`](../shared/asyncapi.yaml) (the five `fulfillment.stock.*` request/reply schemas and the three `stock.*` fact payloads). They are **not restated here** — this file adds only the local requirements (`FS<n>`) for gaps the shared spec leaves to each assessment, and the traceability for them.
>
> **Id reuse is a claim.** `FS2` – `FS17` reuse #7's local ids (`order-to-cash-nestjs/specs/fulfillment_stock/requirements.md`) as an explicit assertion that the .NET realisation carries **the same obligation**, checked one by one against #7's committed code before the id was written down. `FS18` – `FS22` are **new to #8**, and each names why #7 could not have faced it — in every case a property #7's engine, language or framework supplied for free. **`FS1` is deliberately not reused**: see §1.1.
>
> **Scope note on `R36`.** `R36` (`despatch.create`) is listed in the shared §4 range but its responder is feature 18 `fulfillment_despatch`. This feature delivers only the aggregate half it depends on — `Consume(orderReference)` on `StockItem` and the `reserved → consumed` edge of the lifecycle (`R35`) — and leaves the `R36` matrix row `TODO` for feature 18 to flip. Likewise `R61`'s **API** half (`api/stock-replenishment.spec`) belongs to the Gateway (feature 25); only its domain-unit half flips here.
>
> Related shared requirements this feature composes with but does not own: `R13`/`R14`/`R15` (the outbox, the relay and the partition key — Fulfillment's own copies are proven against them here, the rows stay owned by feature 14), `R17`/`R18` (the idempotent-consumer pattern — **not** copied into this service, see `design.md` §9 and the gate row that rules on it), `R29` (the orchestrator's retry and `(orderReference, operation)` idempotency — the **responder** side of that contract is this feature's `FS5`, `FS9`), `R12` (`correlationId`/`causationId` chains — `FS2`, `FS3`).

## 1. Local requirements — `FS<n>`

### 1.1 What #7's `FS1` asked for, and why #8 does not claim it

#7's `FS1` obliged the orchestrator to (a) survive a distinct-`eventId` duplicate of a fact whose step still owes a command, without failing the consumer's transactional unit on the `(order_id, command)` unique key, **and** (b) re-dispatch the existing row on the fast path exactly as a freshly enqueued one.

**Half (a) is already true in #8 and was true before this feature.** `src/Orders/Infrastructure/Saga/EfCoreSagaCommandStore.EnqueueAsync` catches the duplicate-key `SqlException` (2601/2627), detaches the poisoned entry and returns `EnqueueOutcome.AlreadyEnqueued` — a value the port has carried since phase 8. There is no crash-loop to fix.

**Half (b) is deliberately absent.** `SagaFactHandler` logs the already-owed outcome and does **not** signal a second dispatch, so the existing `pending`/`parked` row is re-issued by the sweeper on its own schedule (`SO5`, `SO11`; `OrdersSagaSweeperOptions.IntervalMs` 30 s, park backoff capped at 15 min) rather than immediately. The difference between #7 and #8 on this path is **latency, not durability** — no command is lost either way. Reusing the id `FS1` would therefore be a false claim, and this feature makes no Orders change on that path. Recorded in `progress/spec_fulfillment_stock.md` row 3.

### 1.2 Orders side — what the first real responder forces

**FS2.** WHEN the orchestrator issues any of the five saga commands over the RPC transport, THE SYSTEM SHALL carry the request headers `x-correlation-id` = the order id and `x-request-id` = the id of the durable `saga_commands` row being dispatched, and SHALL carry the **same two values** on every in-line retry and every sweeper re-issue of that row (`asyncapi.yaml` `RpcHeaders`: *"a retry after a timeout reuses the same value, which is what lets a responder recognise a duplicate"*). The `stock.check` call made at order acceptance SHALL carry neither header, because no order exists yet.

### 1.3 Wire contract of the responders

**FS3.** WHEN Fulfillment emits a fact in response to a `stock.reserve` or `stock.release` command, THE SYSTEM SHALL set the fact's `correlationId` from the request's `x-correlation-id` header and its `causationId` from the request's `x-request-id` header (`R12`); IF either header is absent or is not a well-formed `UniqueId`, THEN THE SYSTEM SHALL reply `RpcError` `VALIDATION_FAILED`, SHALL mutate no stock item and SHALL emit no fact. `stock.check`, `stock.list` and `stock.replenish` SHALL require neither header.

**FS4.** THE SYSTEM SHALL accept each of the five `fulfillment.stock.*` requests as a **bare JSON** payload matching the AsyncAPI request schema — no framework packet envelope around it — and SHALL reply with a **bare JSON** success payload or a bare JSON `RpcError`, serialised through the one shared `JsonWire.Options`; a responder SHALL never reply with anything else and SHALL never leave a request unanswered on any path it can reach.

### 1.4 `stock.reserve` — idempotency, locking, the race, unknown products

**FS5.** WHILE reservation rows already exist for the request's `orderReference` — **in any status**, including `released` and `consumed` — THE SYSTEM SHALL reply to `stock.reserve` with `outcome: already_reserved` carrying the existing reservation references, SHALL change no `reservedUnits`, SHALL create no reservation and SHALL emit no second `stock.reserved.v1` (`saga.md` §6 layer 3, `R29`'s responder half). *(#7 shipped this branch implemented but untested and was **rejected** for it — a status filter added to the short-circuit survived its entire suite. `tasks.md` names the guard and arms exactly that mutation.)*

**FS6.** WHEN executing `stock.reserve`, THE SYSTEM SHALL acquire an exclusive lock on every stock row named by the order's lines **before** evaluating availability or reading the order's existing reservations, so that IF two `stock.reserve` commands for different orders compete for the last units of one item concurrently, THEN exactly one commits a reservation and emits `stock.reserved.v1` and the other emits `stock.rejected.v1` naming the shortage — never both reserving, never a deadlock between them.

**FS7.** IF a line was reported `sufficient` by an earlier `stock.check` and is no longer satisfiable when `stock.reserve` runs, THEN THE SYSTEM SHALL reject per `R33` exactly as it would have without the earlier check — the check is a non-locking read that holds nothing (`R31`) and its reply is never a promise; the rejection is a legitimate, intended outcome the saga compensates (`saga.md` §4.1), not an error.

**FS8.** IF any line of a `stock.reserve` request names a `productCode` for which no stock item exists under the request's `companyCode`, THEN THE SYSTEM SHALL treat that line as short with `available: 0`, SHALL create no reservation for any line (`R33`, **F3**), and SHALL emit `stock.rejected.v1` with `reason: unknown_product`; WHEN every line names a known item and at least one is short, the reason SHALL be `insufficient_stock`.

### 1.5 `stock.release` — the two edges `R34` leaves open

**FS9.** WHEN `stock.release` is received for an `orderReference` that holds **no** reservation row at all, THE SYSTEM SHALL reply `outcome: already_released` with an empty `released` list, SHALL change no counter and SHALL emit no fact — the same success no-op as `R34`'s all-already-released case, because an order that never held stock has nothing to unwind (`saga.md` §4.1).

**FS10.** IF `stock.release` is received for an order whose reservations are in status `consumed`, THEN THE SYSTEM SHALL reply `RpcError` `PRECONDITION_FAILED`, SHALL change no reservation and no counter and SHALL emit no fact (**F4**, `R35` — a consumed reservation is terminal; the goods left, and cancellation is impossible from `despatched` onwards per Table T-1).

### 1.6 The aggregate — consume, the derived counter, the fact's aggregate identity

**FS11.** WHEN `Consume(orderReference)` is invoked on a stock item holding reservations in status `reserved` for that order, THE SYSTEM SHALL set those reservations to `consumed`, SHALL decrease both `units` and `reservedUnits` by their total, and SHALL append **no** domain event — the fact that accompanies consumption is `order.despatched.v1`, emitted by the `DespatchAdvice` aggregate in feature 18 (`domain-model.md` §4.2, table row `reserved → consumed`).

**FS12.** THE SYSTEM SHALL reconstitute a `StockItem` from its stored `units`, `reservedUnits` and the reservation rows loaded with it, and after every committed `stock.reserve`, `stock.release` and `Consume` transaction THE SYSTEM SHALL leave `reserved_units` equal to the sum of `units` over that item's reservations in status `reserved` (**F2** — the counter is a derived cache of the ledger and is mutated only in step with it, inside the same transaction).

**FS13.** THE SYSTEM SHALL set the `aggregateId` of `stock.reserved.v1` and `stock.rejected.v1` to the id of the stock item named by the **first line** of the request that resolves to a known item, and the `aggregateId` of `stock.released.v1` to the id of the stock item of the first reservation released, so that every order-scoped Fulfillment fact carries a real aggregate identity (`domain-model.md` §7.1) even though one `stock.reserve` transaction touches one stock item per distinct product (**F3** — see `design.md` §4.2 for the documented tension with §8 rule 6).

### 1.7 `stock.replenish`, `stock.list` and `stock.check`

**FS14.** IF any line of a `stock.replenish` request names a `productCode` with no stock item under the request's `companyCode`, THEN THE SYSTEM SHALL reply `RpcError` `NOT_FOUND` naming that product and SHALL replenish **no** line of the request (all-or-nothing, so a partially applied top-up cannot exist); WHEN every line is known, THE SYSTEM SHALL apply `R61` to each and reply the affected items as `StockView`s.

**FS15.** WHEN `stock.list` is received, THE SYSTEM SHALL reply `StockView` items with `availableUnits = units − reservedUnits`, ordered by `(companyCode, productCode)`, paged per `PageRequest` defaults (`page` 1, `pageSize` 25, maximum 200), filtered by `companyCode` and `productCode` when present, and WHERE `belowThreshold` is `true` SHALL return only items whose `availableUnits < lowStockThreshold`; the query SHALL mutate nothing and take no lock.

**FS22.** WHEN `stock.check` receives a well-formed request, THE SYSTEM SHALL answer with a `StockCheckReplyPayload` in every case — a `productCode` with no stock item under the request's `companyCode` SHALL be answered `available: 0, sufficient: false`, never as an error — and SHALL reserve an `RpcError` reply for a malformed request or an internal failure. *(New in #8. It matters because `src/Orders/Infrastructure/Messaging/NatsStockAvailabilityChecker` deserialises the reply body as `StockCheckReplyPayload` with **no** `RpcError` discriminator: an error reply there yields `Lines = null` and the next line throws a bare `NullReferenceException`. Feature 46 `orders_stock_check_rpc_error_discriminator` owns that fix and this feature must not absorb it — `FS22` bounds the exposure by keeping the error reply off the ordinary acceptance path.)*

### 1.8 The facts leave through Fulfillment's own outbox

**FS16.** THE SYSTEM SHALL write `stock.reserved.v1`, `stock.rejected.v1` and `stock.released.v1` as outbox rows in the **same transaction** as the reservation rows and `reserved_units` changes they describe (`R13`), and SHALL publish them to `otc.fulfillment.facts.v1` **only** through Fulfillment's own outbox relay, keyed by `correlationId` (`R14`, `R15`) — no responder, handler or aggregate publishes directly.

### 1.9 New to #8 — properties #7 got for free

Each of these exists because a property that #7's engine, language or framework supplied implicitly must be **constructed** in .NET / MS-SQL. They are the executable half of `design.md` §15's ported-idiom ledger.

**FS18.** WHILE one `fulfillment.stock.*` request is being handled and is blocked — on a database row lock, on I/O, or on anything else — THE SYSTEM SHALL begin handling a further request on the same or another `fulfillment.stock.*` subject rather than serialising it behind the first, up to a bounded maximum of concurrently handled requests, and SHALL handle each request in its own dependency-injection scope so that no two in-flight requests share a `DbContext`. *(#7's `@nestjs/microservices` NATS server handled every request on its own promise chain, so this was free. #8's only responder precedent, `src/Orders/Presentation/OrdersCreateResponder`, is **deliberately sequential** — its own remark says "Revisit if a later feature adds a second concurrent RPC subject this responder must not block". Copying that shape would make `FS6`'s race test pass **for the wrong reason**: two serialised reserves also produce one `accepted` and one `rejected`, so the test would be green while proving nothing about the lock.)*

**FS19.** WHEN a transaction takes locks on more than one stock row, THE SYSTEM SHALL take them **one row at a time, in a total order fixed by the application** — ascending ordinal order of the invariant-uppercased `productCode`, over the distinct product codes of the request compared case-insensitively — and SHALL take every read whose result decides idempotency or availability under an explicit lock hint; THE SYSTEM SHALL NOT depend on the query planner's row-access order, on an `ORDER BY` inside a locking statement, or on the ambient isolation level for either property. *(#7 got the total order from InnoDB's index scan and got blocking reads from `FOR UPDATE` under `REPEATABLE READ`. `READ_COMMITTED_SNAPSHOT` is **ON** for every database here — `infra/mssql/init/01-create-databases.sql` — so an un-hinted read takes **no lock at all** and sees a row version, and MS-SQL gives no guarantee about the order in which a multi-row seek acquires its locks.)*

**FS20.** IF a `stock.replenish`, `stock.reserve` or reconstitution operation would compute a unit count outside the representable range of the stored counter, THEN THE SYSTEM SHALL raise a domain error carrying a stable code and change nothing — no counter SHALL ever wrap, become negative by arithmetic overflow, or silently truncate. *(#7's JavaScript numbers have no narrowing conversion and cannot wrap. C# `int` arithmetic is **unchecked by default** — `Directory.Build.props` sets no `CheckForOverflowUnderflow` — and `units`/`reserved_units` are `int` columns, so `units + quantity` wraps to a negative value in silence. This is the same shape as the money-truncation defect recorded in `CLAUDE.md`'s ledger table.)*

**FS21.** IF a `stock.reserve` or `stock.release` transaction fails for a **transient** store reason — a deadlock victim, a connection failure, a lock timeout — THEN THE SYSTEM SHALL reply with an `RpcError` whose `code` is one of the transient codes `UNAVAILABLE`, `TIMEOUT` or `INTERNAL_ERROR`, and SHALL NOT reply with any of the nine codes `src/Orders/Infrastructure/Messaging/NatsSagaCommandsAdapter.IsTerminalRpcErrorCode` classifies as a terminal business rejection (`VALIDATION_FAILED`, `NOT_FOUND`, `CONFLICT`, `PRECONDITION_FAILED`, `ORDER_NOT_CANCELLABLE`, `STOCK_UNAVAILABLE`, `INVOICE_NOT_PAYABLE`, `PAYMENT_MISMATCH`, `DOMAIN_ERROR`). *(#7 mapped its `ConcurrentReservationChangeError` to `CONFLICT` and its orchestrator retried it. In #8, feature 42 made `CONFLICT` **terminal**: the saga command row would be marked `rejected`, a status `ClaimDueAsync`'s predicate structurally never re-claims, so a retryable failure would end the order's saga for good. The requirement text of `FS6`/`R32` would still be satisfied — this is exactly the class of defect the ledger exists to catch.)*

### 1.10 First boot against the live stack

**FS17.** WHEN the Fulfillment responders first start against the deployed compose stack, whose `otc_orders.saga_commands` holds four `parked` `stock.reserve` rows (`ORD-000007` … `ORD-000010`, each `attempts = 6`, last error *"no responder"*), THE SYSTEM SHALL answer the sweeper's next re-issue of each row **without operator action**, so that each such order either gains reservation rows plus one published `stock.reserved.v1` in `otc_fulfillment.outbox` and advances in Orders to `stock_reserved` with a new `credit.hold` row that parks (Billing does not exist yet), or receives `stock.rejected.v1` and moves to `cancelled` with **no** `stock.release` row (`R26`). *(Designed in `design.md` §12; verified live, not by an automated test.)*

## 3. Promotion candidates (for a later shared pass, not edited now)

These are the same five #7 raised, re-verified against #8's reading of the shared documents. Recording them again is not duplication: a promotion candidate that only #7 recorded would be invisible to whoever eventually does the shared pass from #8's side.

- **`FS2`/`FS3` — the correlation carrier.** `asyncapi.yaml`'s `RpcHeaders` documents `x-correlation-id` and `x-request-id`, but no shared requirement *obliges* the caller to send them or the responder to derive `correlationId`/`causationId` from them. Without that sentence, `R12` is unsatisfiable for any fact a responder emits, because the request payloads carry only `orderReference`. Candidate wording for `requirements.md` §2: *"WHEN a command concerning a known order is issued over the RPC transport, THE SYSTEM SHALL carry the order id as `x-correlation-id` and a per-command-record id as `x-request-id`, and a responder SHALL stamp the facts it emits in response with that `correlationId` and that `causationId`."*
- **`FS13` and `domain-model.md` §8 rule 6.** *"One transaction mutates exactly one aggregate instance plus its outbox records"* and **F3** *"either every line of the order is reserved, or none is"* cannot both hold literally when an order's lines name different products. The shared model should say which yields. Both assessments answer **F3**, with a deterministic lock order and a single carrier aggregate for the fact's identity.
- **`FS5` (repeat-reserve against a released/consumed order).** `saga.md` §6 says a second `stock.reserve` "returns the existing reservation without double-reserving" but does not say what "existing" means once those reservations are terminal. Both assessments answer *any* reservation rows for the order, whatever their status.
- **`FS9`/`FS10`** (release of a never-reserved order; release of a consumed order) are edges `R34` leaves open; both are cheap to state in the shared §4.
- **`FS21` — the retryability of an `RpcError` code.** `asyncapi.yaml` fixes a twelve-value `RpcError.code` enum but says nothing about which values a caller may retry. #8 had to split them (feature 42) and a responder now has to know the split, which makes it a cross-assessment contract rather than a caller-local policy. Candidate: one sentence in `asyncapi.yaml`'s `RpcError` description naming the terminal set. **New from #8 — #7 did not raise it, because #7's orchestrator retried every code.**
