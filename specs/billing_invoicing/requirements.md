## 1. Local requirements — `BI<n>`

### 1.1 The command surface, and what may trigger an invoice

**BI1.** THE SYSTEM SHALL issue an invoice **only** in response to a `billing.invoice.issue` NATS RPC request, and the Billing service SHALL register **no** Kafka consumer, **no** fact-stream `BackgroundService` and **no** idempotent-consumer runner of any kind — `saga.md` §5 gives Billing no consumed facts, and the orchestrator is the only component permitted to translate `order.despatched.v1` into the issue command (`saga.md` §3.1 step 4). IF a fact-stream consumer is introduced into the Billing service, THEN the structural guard of `BI1` SHALL fail.

> **Why this requirement exists.** `feature_list.json`'s acceptance line for this feature reads *"issued on OrderDespatched"*, which reads like an instruction to subscribe to `order.despatched.v1`. It is not. The causal chain is `order.despatched.v1` → orchestrator → `invoice.issue` → `invoice.issued.v1`, and a Billing-side Kafka consumer would duplicate the trigger, bypass the saga's dedup record and its order-status precondition (`saga.md` §6 layers 1 and 2), and put a second, unsequenced writer on the invoice. In #8 the guard is not a text scan for a decorator (#7 had no other option, and its own review recorded that limitation as `N8`): the guard enumerates the service's registered `IHostedService` implementations from the **real built host** and asserts the set is exactly `{ OutboxRelayBackgroundService, BillingRpcResponder }`, and additionally that no `Confluent.Kafka` consumer type is referenced anywhere under `src/Billing/`.

**BI2.** WHEN a `billing.invoice.issue` request arrives whose `x-correlation-id` or `x-request-id` header is absent or is not a well-formed `UniqueId`, or whose payload fails schema validation — an empty `lines` list, a non-positive `units`, a negative `unitPrice`, a malformed `orderReference`, a currency that is not `^[A-Z]{3}$`, a negative `discount`, **or a `discount` that exceeds `Σ(unitPrice × units)`** — THE SYSTEM SHALL answer `VALIDATION_FAILED` **before dispatching the command**, SHALL create no invoice, SHALL append no ledger entry and SHALL emit no fact.

> **The placement clause is proven by observing the entry, never the residue.** #7 was **rejected** on this requirement (its review's blocking finding `N2`: the discount check sat inside the transaction and reached the global sequence counter before refusing), and its round-2 re-review then found (`N10`) that the integration assertion credited with proving the fix *could not distinguish the two placements*, because a rolled-back counter is byte-identical whether it was touched or not. The general lesson, in that review's own words, is inherited verbatim: *an assertion that a rolled-back side effect did not happen proves nothing about whether it was attempted; to prove a code path was never entered, observe the **entry** — a bus that was never called, a lock that was never requested — never the **residue**.* `BI2`'s placement clause is therefore discharged by a **unit** case asserting `IDispatcher.SendAsync` was never called; the integration case asserts the observable outcome, and says in its own comment that it does not prove placement.

**BI3.** IF a `billing.invoice.issue` request names a `(retailerCode, companyCode)` pair for which no credit line exists, THEN THE SYSTEM SHALL answer `NOT_FOUND` naming the pair, SHALL create no invoice, SHALL append no ledger entry and SHALL emit no fact.

**BI4.** IF a `billing.invoice.issue` request names a `currency` other than the credit line's, THEN THE SYSTEM SHALL answer `VALIDATION_FAILED` carrying the expected and the received currency, SHALL create no invoice, SHALL append no ledger entry and SHALL emit no fact (a consequence of **M2** and of **B3**).

**BI5.** IF a `billing.invoice.issue` request names an order that holds **no active credit hold** on the named credit line — because the hold was refused, because a cancellation already released it, or because no hold was ever placed — THEN THE SYSTEM SHALL answer `PRECONDITION_FAILED` carrying the stable code `NO_ACTIVE_HOLD`, SHALL create no invoice, SHALL append no ledger entry, SHALL emit no fact, and SHALL leave the order's existing ledger rows exactly as they were.

> **Why `PRECONDITION_FAILED` and not an invoice.** Billing owns no order status and may not read the Orders write model (`domain-model.md` §1 boundary rule 1), so it cannot check `R45`'s literal precondition *"an order in status `despatched`"*. The active hold is the only order-scoped state Billing owns, and by the saga's construction every order reaching step 4 has one. Its absence therefore means the two write models disagree — a condition a retry cannot fix and a human must see. The final clause (*"leave the order's existing ledger rows exactly as they were"*) is #7's review finding `N3`, which found that clause written and never asserted; it is asserted here from the start.

**BI6.** THE SYSTEM SHALL emit **no fact other than `invoice.issued.v1`** in response to a `billing.invoice.issue` request, on any path it can reach. There is no invoice-rejection fact in the catalogue of `domain-model.md` §7.2, so every non-success outcome of this subject is an `RpcError` reply and every success is either a new invoice carrying exactly one fact or an idempotent repeat carrying none.

### 1.2 The transaction, the ledger and the locks

**BI7.** WHEN an invoice is issued for an order holding an active credit hold, THE SYSTEM SHALL, **in one database transaction**, insert the invoice row and its line rows, append exactly one `consume` ledger entry of that order's active hold to the `BuyerCredit` aggregate, and record exactly one `outbox` row, whose `event_type` is `invoice.issued.v1`; and IF any of those writes fails, THEN THE SYSTEM SHALL roll back all of them, leaving no invoice row, no invoice line, no ledger entry and no outbox row, and SHALL answer with an error reply.

> **This transaction deliberately mutates two aggregates**, contrary to the default of `domain-model.md` §8 rule 6. The deviation is re-derived against #8's own code in `design.md` §7.4 — **not** inherited on #7's citation — and it holds more cleanly here than there, because #8 has no `TransactionContext` to thread: both repositories enlist in the ambient transaction of the one scoped `BillingDbContext`. The justifying invariant is one no single aggregate owns — *an issued invoice's hold is consumed* — and the alternative leaves a crash window that **nothing can detect**, because `R40`'s `consume` deliberately emits no fact and the saga can only compensate what it observes.

**BI8.** THE SYSTEM SHALL acquire row locks in the Billing write model in exactly one order — `credits` (and its `credit_items`), then `invoices`, then `invoice_number_sequences` — in every transaction of the service, present and future; and two concurrent `billing.invoice.issue` requests for the same order SHALL produce exactly one invoice, exactly one `consume` entry and exactly one `invoice.issued.v1`, with no deadlock and no lock-wait timeout.

> **All three locks are guarded, not two.** #7 shipped an ordered-call-log unit test covering only the first two, and its review recorded (`N4`) that moving the allocator above the invoice read would have left every test green — the half its own design argued hardest for, and the half feature 22 must inherit. #8's ordered call log records **three** calls and asserts the three-element sequence.
>
> **Binding on feature 22.** `billing.payment.register` identifies its invoice by `invoiceReference`/`invoiceId` and must therefore read the invoice row **without a lock** to discover the `(retailerCode, companyCode)` pair, then take the `credits` lock, then re-read the invoice row under `WITH (UPDLOCK, HOLDLOCK, ROWLOCK)` and re-verify its status. Locking the invoice first would close a cycle with this feature's ordering and deadlock under concurrent payment and re-issue.

**BI9.** WHILE an invoice already exists for the `orderReference` named by a `billing.invoice.issue` request, THE SYSTEM SHALL answer with the existing `invoiceId`, `invoiceReference`, `invoiceDate`, `currency`, `totalAmount` and current `status`, with `created: false`, SHALL write nothing at all — no second invoice, no second `consume` entry, no row of any kind — and SHALL emit no second fact (invariant **B7**, `saga.md` §6 layer 3). This holds whether the existing invoice is `issued` or already `paid`.

### 1.3 The aggregate

**BI10.** THE SYSTEM SHALL make an invoice whose status is `paid` without a `paidAt`, or whose status is `issued` with a `paidAt`, **unrepresentable in the domain layer**: the two are one value, not two independent fields, and no member of the aggregate assigns either of them separately; and IF a stored row is reconstituted whose `status` and `paid_at` disagree, THEN THE SYSTEM SHALL raise a domain error naming the invoice rather than construct the aggregate (invariant **B9**).

**BI11.** THE SYSTEM SHALL derive an invoice's `amount` as `Σ(unitPrice × units)` over its lines and its `totalAmount` as `amount − discount`, SHALL refuse construction when the line list is empty, when a line's currency differs from the invoice's, or when `totalAmount` would be negative, and SHALL expose no setter for any of `amount`, `discount` or `totalAmount` (invariant **B6**). `Quantity` already refuses zero and negative unit counts at construction, so the non-positive-units clause needs no separate check inside the aggregate.

**BI12.** THE SYSTEM SHALL allocate each `invoiceReference` as `INV-` plus a zero-padded six-digit sequence, unique across the service and never reassigned, using the same single-row counter-table mechanism `ORD-` and `DES-` use; two concurrent allocations SHALL never yield the same value; and the first live allocation SHALL continue past the highest reference the seed already wrote (`INV-000005`) rather than colliding with it.

**BI13.** THE SYSTEM SHALL stamp `invoice.issued.v1` with `aggregateId` = the invoice's own id, `correlationId` = the order id taken from `x-correlation-id`, `causationId` = the request id taken from `x-request-id`, and `occurredAt` = the invoice's `invoiceDate` read once from the clock port — one event type, one builder, one call site; and the test that proves it SHALL prove **provenance**, by driving the id source and the clock through injected delegates and asserting the stamped values are the delegates' returned values, never merely that they are non-default and distinct.

**BI14.** WHERE feature 22 is not yet implemented, THE SYSTEM SHALL nevertheless provide `Invoice.MarkPaid`, which moves an `issued` invoice to `paid`, sets `paidAt` in the same indivisible assignment, and appends exactly one `payment.received.v1` carrying the payment's own reference, amount, currency, value date and source; and IF `MarkPaid` is called on an invoice already `paid`, or with an amount or currency other than the invoice's `totalAmount` and currency, THEN THE SYSTEM SHALL raise a domain error, change nothing and append no event (invariants **B8**, **B9**, **B10**; shared `R46`, and the amount clause of `R49`).

### 1.4 The read side

**BI15.** WHEN a `billing.invoice.list` request is received, THE SYSTEM SHALL answer with a page of invoice views filtered by any supplied `status`, `retailerCode`, `companyCode` and `orderReference`, SHALL return only invoices whose `invoiceDate` is at least `issuedBeforeMinutes` minutes before the current time when that filter is supplied, SHALL take the current time from the clock port as a parameter rather than reading an ambient system clock inside the query adapter, SHALL take no lock and open no transaction, and SHALL never mutate anything.

**BI16.** THE SYSTEM SHALL answer both new subjects with **bare JSON** — a plain reply object on success and a plain `RpcError` object on failure, with no framework packet envelope — through the one shared `JsonWire.Options`; and the subject constants SHALL equal the `address` of their AsyncAPI channels character for character, read from `specs/shared/asyncapi.yaml` as text rather than retyped.

### 1.6 New to #8 — properties #7 got for free, or contract surface #7 did not have

**BI23.** THE SYSTEM SHALL render the invoice's `(status, paidAt)` pair as a **closed abstract reference hierarchy** with exactly two cases, whose base type is abstract and whose only instance constructor is inaccessible outside the domain assembly, so that no third state and no partially-initialised state is constructible; and the aggregate SHALL hold exactly one field of that type.

> *New to #8. #7 got closure and non-nullability from a TypeScript **structural** discriminated union: `{status:'paid'; paidAt: Date}` cannot be written without its `paidAt`, and there is no "zero value" of a union. C# has no structural unions, and the two obvious renderings differ in exactly the property that matters: a `readonly record struct` with a private constructor still has `default(T)` — always constructible, satisfying neither case, and silently reachable through an uninitialised field or an array allocation — so it **loses** the property #7 had. The abstract-record rendering keeps it. This requirement records the property, not the syntax, so that the choice is auditable. This is the **second** time in this build that a #7 property came from TypeScript being structurally typed; the first was the outbox writer's shape-resolved mapper in feature 19 (`billing_credit/design.md` §15 `L27`). `design.md` §16's preamble records the pattern.*

**BI24.** THE SYSTEM SHALL round-trip `paid_at` through the store such that an instant written as UTC is read back as the identical instant regardless of the host's local time zone, and SHALL distinguish a `NULL` `paid_at` from an instant — the nullable case included in the guard, not only the non-null one.

> *New to #8. #7's `mysql2` pool was created with `timezone: 'Z'`, one clause, and every date crossed the boundary correctly for free. #8 stores `datetime2(3)`, which carries no offset, and EF Core hands back `DateTimeKind.Unspecified`; `new DateTimeOffset(unspecified)` applies the **machine's local** offset. Feature 19 supplied this for `credit_date` (`BC24`, ledger `L11`) and armed it. `paid_at` is the first **nullable** instant column any #8 aggregate reads, and the null-conditional rendering (`row.PaidAt is null ? null : new DateTimeOffset(...)`) is exactly where the `SpecifyKind` call is easiest to drop.*

**BI25.** IF an invoice's `Σ(unitPrice × units)` or `amount − discount` would exceed the representable range of the money type, THEN THE SYSTEM SHALL raise a **domain error carrying a stable code**, never an unhandled framework `OverflowException`, and the responder SHALL map it to a code the saga dispatcher classifies as **terminal**.

> *New to #8. JavaScript has one number type and no narrowing or overflow: #7 had nothing to supply. #8's `Money.Add`/`Subtract`/`Multiply` became `checked` at the Phase-10 gate (`billing_credit/design.md` §15 `L25`), so the arithmetic **raises** — but `OverflowException` has no `Code`, falls to `BillingErrorMapper`'s `_ =>` arm as `INTERNAL_ERROR`, and `NatsSagaCommandsAdapter.IsTerminalRpcErrorCode` classifies `INTERNAL_ERROR` as **transient**, so a permanently-overflowing payload would be retried to exhaustion on every sweep. `CreditExposure.Summarise`'s `checked { … } catch (OverflowException) { throw new CreditLedgerOverflowError(…); }` is the exact shipped precedent, and `CreditLedgerOverflowError` is already mapped to the terminal `DOMAIN_ERROR`.*
>
> **And the same hazard exists one layer up.** `BI2`'s cross-field check (`discount > Σ(unitPrice × units)`) is itself `long` arithmetic in the validator, and C# arithmetic is **unchecked by default** — `CheckForOverflowUnderflow` is not set in `Directory.Build.props`. A validator that wraps would pass a payload the domain then refuses inside the transaction, which is precisely the placement defect `BI2` exists to prevent. The validator therefore performs its sum inside an explicit `checked` region and reports a validation error on overflow.

**BI26.** THE SYSTEM SHALL classify `PRECONDITION_FAILED` as a **terminal** saga rejection, so that a `BI5` refusal stops the `invoice.issue` command row immediately with the reason recorded, rather than being retried to exhaustion; and a test SHALL read that classification from the dispatcher's own closed set rather than restating it.

> *New to #8 in mechanism, identical in intent. #7's justification for `BI5` was "the saga dispatcher retries and then parks the row, which is exactly the desired handling" — the property being *a human must see it, because a retry cannot fix it*. #8 supplies the same property more directly: feature 42 made nine `RpcError` codes terminal, `SagaCommandDispatcher` short-circuits the retry loop on a terminal rejection and calls `RejectAsync` with the message, logging at `Error`. The property is preserved and the realisation is strictly more direct; this requirement exists so the dependency is explicit rather than accidental.*

**BI27.** THE SYSTEM SHALL treat the invoice `status` token as a closed set (`issued`, `paid`) parsed **loudly** — an unrecognised token raises rather than being coerced or skipped — and SHALL write only the lower-case contract tokens, so that MS-SQL's case-insensitive column collation and the domain's ordinal comparison can never disagree about which invoices a filter selects.

> *New to #8. #7 compared status strings with JavaScript `===` against a TypeScript union that no unknown value could inhabit. #8's `status` is an `nvarchar(20)` under `SQL_Latin1_General_CP1_CI_AS`: `WHERE status = 'paid'` matches a row written `'Paid'`, while `string.Equals(…, StringComparison.Ordinal)` in the mapper does not. This is `L13`/`L14`'s sibling from feature 19, closed the same way — at the edge, by a total parse and a single writer.*

**BI28.** THE SYSTEM SHALL declare Billing's own `billing.invoice.*` request and reply records carrying **exactly** the property names `asyncapi.yaml` declares, asserted against the property list **parsed from the spec** rather than retyped; and an `InvoiceView` whose invoice is `issued` SHALL omit the `paidAt` key entirely rather than emit it as `null`.

> *New to #8 in both halves. The first half is `BC23`'s obligation (backlog id 51) extended to two more subjects — C# has no generated contract type for RPC payloads, so the records are hand-transcribed and the parsed-from-spec check is what makes following the contract mechanical. The second half is a **deliberate, recorded divergence from #7's bytes**: #7's design says `paidAt` is serialised "as an ISO string or `null`", while #8's ratified non-negotiable is `camelCase`, **nulls omitted**, set once in `JsonWire.Options` "so no service can drift" (`CLAUDE.md`, Architecture non-negotiables). `asyncapi.yaml` leaves `paidAt` out of `InvoiceView.required` and declares it `oneOf [Instant, null]`, so both shapes validate; applying the ratified rule is not a new decision. Consumers must read an **absent** `paidAt` as "not paid": the Gateway (feature 25) and the n8n bank robot (feature 33) are the two, and `design.md` §18 carries it as a hand-over.*

**BI29.** THE SYSTEM SHALL seed the `invoice_number_sequences` counter row **atomically** — one statement whose insert and whose existence test are the same statement — never as a check-then-act pair; and the seed value SHALL continue past the highest `INV-` reference already present in `invoices`.

> *New to #8, and it is a defect this repository has already paid for once. #7 got atomicity from MySQL's `INSERT … ON DUPLICATE KEY UPDATE`, where the statement **is** the unit of atomicity. #8's first rendering of that idiom for `ORD-` was `IF NOT EXISTS (SELECT …) INSERT` — check-then-act — found by a later feature's reviewer reading the SQL and fixed in feature 45; `EfCoreDespatchNumberAllocator` carries the fixed idiom and a header explaining it. The `INV-` allocator is the third instance and is a verbatim copy of the fixed one, not a re-derivation.*

**BI30.** THE SYSTEM SHALL make `BC32`'s universal claim true rather than narrowed: **every** integration test that deserialises an RPC reply SHALL assert that reply's own discriminating field before it touches any collection, and the claim SHALL be evidenced by an enumerating command and its complete output, not by a prose sweep.

> *New to #8 — backlog id 55, raised by feature 19's own review round 2. Six sites still violate it: `tests/Billing.IntegrationTests/CreditListTests.cs` lines 39, 73 and 77, and `tests/Fulfillment.IntegrationTests/StockListTests.cs` lines 33, 38 and 44. #7 could not face this: it deserialised into a JavaScript object and read `undefined`, which its assertions caught; C# deserialises an `RpcError` body into an all-defaults reply record **without throwing**. The Billing three are in a file this feature opens; the Fulfillment three are reachable by the same one-line pass and are included so the entry closes rather than half-closes. A `DONE` traceability row resting on a false universal claim is the shape feature 19 already spent a review round on.*

**BI31.** THE SYSTEM SHALL answer all five `billing.*` RPC subjects from **one** `BackgroundService`, so that the service's request-concurrency bound, its one-`IServiceScope`-per-request rule and its individually-awaited shutdown drain exist in exactly one implementation guarded by exactly one set of tests.

> *New to #8, and the reason is a stack difference. #7 declared a second `@Controller` and inherited concurrency, per-request DI scope and graceful shutdown from NestJS. In #8 all three are hand-built inside `CreditRpcResponder` and each is guarded by a named test (`BC21` scope-per-request, `BC22` drain and fault isolation, backlog id 50). A second responder class would fork four armed behaviours; `CLAUDE.md`'s non-negotiable is **one `BackgroundService` per transport**, and Billing's RPC transport is one. The class, its options, the error mapper and the fact-payload mapper therefore become service-scoped rather than credit-scoped. **Flagged for the gate** — `progress/spec_billing_invoicing.md` row 1.*

### 1.7 First boot against the live compose stack

**BI22.** WHEN the Billing service first starts with the `billing.invoice.issue` responder registered, THE SYSTEM SHALL cause every `invoice.issue` row parked in `otc_orders.saga_commands` to be re-dispatched by the existing sweeper, one invoice to be issued per order, one `consume` entry to be appended per order, one `invoice.issued.v1` to be published per order, each of those orders to reach status `invoiced`, and each credit line's `availableCredit` to be **numerically unchanged** by the whole exercise — **and SHALL then stop there**, because `saga.md` §3.1 step 5 has the saga wait for the outside world: no internal timer, no polling, and no further command until a remittance arrives with feature 22.

### 1.8 What #7's `BI18` and `BI19` asked for, and why #8 does not claim them

Both are already satisfied in #8 by shipped, tested code, so reusing the ids would be a claim about work this feature did not do.

- **`BI18`** (a `CREDIT_FAILURE_RATE` that is not a plain decimal numeral must fail startup) — #7 needed a regex because JavaScript's `Number()` coerces `'0x1'` to `1` and `'  '` to `0`. `CreditSimulatorOptionsLoader.Load` uses `double.TryParse` under `NumberStyles.Float`, which rejects `'0x1'`, whitespace-only, `'abc'` and `'1,000'` outright, and it additionally checks `double.IsFinite` because `"NaN"`/`"Infinity"` **do** parse in .NET and would otherwise slip past the range check (`NaN < 0` and `NaN > 1` are both false). The file's own header already records this as a ported-idiom note. `'1e0'` and `'+0.5'` are accepted, deliberately and with a written reason: `R43` asks for "a number in the closed interval [0, 1]" and not for a narrower numeral shape.
