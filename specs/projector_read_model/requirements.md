# `projector_read_model` — Requirements (assessment #8, .NET)

> **The normative requirements for this feature are `R50` – `R55` in [`specs/shared/requirements.md`](../shared/requirements.md) §7**, elaborated by [`specs/shared/domain-model.md`](../shared/domain-model.md) §7.1 (the envelope), §7.2 (all **fourteen** facts) and §7.3 (the consumption map — the projector is the only consumer that takes every fact); [`specs/shared/saga.md`](../shared/saga.md) §6 (the three idempotency layers) and §7 (*"the read model tolerates disorder"*); [`specs/shared/asyncapi.yaml`](../shared/asyncapi.yaml) (the three fact topics, their `correlationId` partition key, the `projectorConsumes*` operations); and [`specs/shared/openapi.yaml`](../shared/openapi.yaml) (`OrderDetail`, `TimelineEntry` **with its `causationId`**, `ProjectionPending`, `OrderStreamUpdate`, `TimelineStreamEntry`). None of those is restated here. This file cites the `R<n>` ids it realises, reuses #7's local `PR<n>` ids where the .NET realisation satisfies the same obligation (each reuse is a claim, checked one by one against #7's committed code and its review), and adds `PR36` – `PR44`, which exist only because .NET, MongoDB.Driver 3.x or #8's own composition differ.

> **`R11`, `R12`, `R17`, `R18` are inherited, not re-owned.** `R11`/`R12` are the producers' obligation and are `DONE`; the projector renders a human summary for every fact from the envelope alone and keys every document on `correlationId` because `R12` makes that the order id. `R17`/`R18` are the idempotency contract this feature satisfies as a **documented variant** (`PR23` – `PR26`); their matrix rows are `DONE` and are not re-flipped.

> **`R54` and `R55` are shared between this feature and feature 25 (`gateway_rest_auth`).** This feature owns the *producer* half of both — sole writer (`R54`) and the update signal (`R55`) — and none of the consumer half (`GET /orders`, `GET /orders/{id}`, `202 ProjectionPending`, `/orders/stream`). §4 states the seam. `specs/shared/test-matrix.md` §7 **already carries the two-half form** of both rows (inherited from #7's gate row 3), so no shared edit is needed; what this feature's gate supplies is the **ratification** rule 3(b) requires for closing the projector half alone — see [`progress/spec_projector_read_model.md`](../../progress/spec_projector_read_model.md).

> **Amendment A1 is folded in as design, not as an amendment.** #7 discovered eight phases late that timeline entries sharing one `occurredAt` were ordered by luck, rewrote `PR10`, amended `PR15`, added `PR30` – `PR35`, and had to change Billing so the completion pair carried a real causal edge. #8 inherited the amended spec **and** closed the Billing half first (backlog id 57, `progress/impl_completion_pair_has_no_causal_edge.md`, approved 2026-09-07): `credit.released.v1`'s `causationId` is already `payment.received.v1`'s `eventId`. So `PR10` below is the causal-order rule from the start, `src/Seed` already writes `causationId` and stamps `timelineOrderVersion = 2`, and nothing in this feature is rework.

## 1. Vocabulary local to this feature

| Term | Meaning here |
|---|---|
| **read-model document** | One MongoDB document in `otc_read_model.order_timeline`, `_id` = the order id (= `correlationId`, `R12`), in **exactly the shape `src/Seed/Infrastructure/Mongo/OrderTimelineDocument.cs` already writes** — that file is the document-shape precedent and this feature does not invent a second one (`PR41`, `PR44`). |
| **placeholder** | A document created by a fact other than `order.placed.v1`, header fields unknown, `headerComplete: false` (`R53`, `PR8`, `PR9`). |
| **complete document** | `headerComplete: true` — `order.placed.v1` has been applied. |
| **implied order status / status rank** | `PR12`'s table: the status a fact proves has been reached (or none), totalised by an integer so `R52`'s "precedes" is a `$max`, never a state-machine walk. **Document-level only** — never a timeline ordering key (`PR30`). |
| **tie group** | The entries of one document sharing one identical `occurredAt`. The only place `PR10`'s causal tiebreak operates. |
| **causal edge** | Within a tie group, *`p` caused `c`* iff `c.causationId == p.eventId`. Never inferred from `eventType`, a status or a rank. |
| **causal depth** | Distance in causal edges from the nearest cause-less entry of the same tie group; `0` when there is none. |
| **fallback key** | `eventId` ascending — what orders two tied entries no edge separates. Deterministic, causally arbitrary, documented as such (`PR31`). |
| **timeline-order version** | The integer stamped on each document naming which version of `PR10` produced its stored `events` order. **`2`**, equal to `MongoSeedWriter.TimelineOrderVersion` (`PR40`). |
| **dedup key** | `"projector:<eventId>"` — `ConsumerNames.ToToken(ConsumerName.Projector)` + `:` + the id — stored in `processedEventKeys`. The pair of `R17`, never the bare id (`PR23`). |
| **the atomic apply** | The single `FindOneAndUpdateAsync` whose **filter is the idempotency check** and whose aggregation-pipeline update is the whole projection of one fact (`PR6`). |
| **update signal** | Two NATS core **publishes** (no reply subject, no responder, at-most-once) announcing that a document changed. Not a fact and not a command (`PR17`). |
| **the variant** | `src/Projector/Infrastructure/Messaging/IdempotentConsumer.cs` — the MongoDB rendering of the idempotent-consumer pattern, discovered as a *variant* by `tests/Orders.UnitTests/IdempotentConsumerParityTests.cs` because the projector owns no `ProcessedEventConfiguration.cs` (`PR24`). |

## 2. Local requirements

### 2.1 The consumer surface

**PR1.** THE SYSTEM SHALL consume the three fact topics `otc.orders.facts.v1`, `otc.fulfillment.facts.v1` and `otc.billing.facts.v1` through **one** Kafka `BackgroundService` (`ProjectorFactsConsumer`) over the copied `IFactStreamSubscriber` port, under the single consumer group `projector`; and the projector SHALL register **no** NATS subscription of any kind — no responder, no request, nothing that carries a reply subject — because the projector answers no query (`R54`; the Gateway reads the read model directly, feature 25). IF a NATS subscription or a fourth Kafka topic is introduced, THEN the structural guard of `PR1` SHALL fail.

**PR2.** THE SYSTEM SHALL handle **all fourteen** `eventType`s of `domain-model.md` §7.2 (thirteen saga facts plus the diagnostic `order.saga_failed.v1`, which contributes a timeline entry, no status and rank `0`), and SHALL prove that coverage structurally in **both** directions against `OrderToCash.Contracts.Facts.FactCatalog.PayloadTypesByEventType` — the one registry whose own completeness test already compares it against `asyncapi.yaml`: a key with no projection arm SHALL fail a named test, and a projection arm for a type not in the catalogue SHALL fail the same test. See `PR36` for why the catalogue is the routing table and not a second list.

**PR3.** IF a message arrives on a fact topic whose value cannot be parsed as a complete envelope — not valid JSON, not an object, or any of the seven `R11` fields absent, empty or default — THEN THE SYSTEM SHALL log one structured error carrying the topic, partition, offset and reason, SHALL write **nothing** to the read model, SHALL publish **no** update signal, and SHALL acknowledge the message (store its offset); a producer bug is not repairable by redelivery and must not block a partition.

**PR4.** IF a message arrives carrying a well-formed envelope whose `eventType` is not one of the fourteen, THEN THE SYSTEM SHALL log one structured error naming the unknown type, SHALL write nothing, SHALL publish no signal and SHALL acknowledge — and SHALL NOT silently discard it. A bare `return` with no log is the failure `PR2` makes impossible at build time and `PR4` makes visible at run time.

**PR5.** THE SYSTEM SHALL subscribe with `AutoOffsetReset.Earliest` — deliberately the opposite of Notifications' `Latest` and the same as the saga orchestrator's — because the read model is a **derived** store whose defining property is that replaying the topics reconstructs it (`PR15`); a projector that starts at the log head produces a permanently and silently incomplete read model, which is a correctness violation, not a missed email. Guarded by `PR38`.

### 2.2 The document, and the write that maintains it

**PR6.** THE SYSTEM SHALL apply each fact to the read model in exactly **two** MongoDB operations and no others: (1) an `UpdateOneAsync(filter: {_id}, update: $setOnInsert <placeholder>, IsUpsert: true)` that brings the document into existence and by construction changes nothing when it exists (`R53`, `PR8`); then (2) **one** `FindOneAndUpdateAsync` whose **filter** is `{ _id: <orderId>, processedEventKeys: { $ne: <dedupKey> } }` and whose update is a single aggregation pipeline carrying the *entire* projection of that fact — the dedup key, the timeline append and re-sort, the status, the references, the header, `updatedAt` and the version stamp — with `ReturnDocument.After` (`PR42`). THE SYSTEM SHALL NOT read the document in order to decide what to write. IF any code path performs a `Find`/`FindAsync`/`CountDocuments` on `order_timeline` and then issues a write derived from what it read, THEN this requirement is violated **even if every test passes**: idempotency here is a property of the query, never of a read-then-write. Proven by recording the driver's command stream (`PR6`'s test uses `MongoClientSettings.ClusterConfigurator` command monitoring) — the only way to prove the absence of a read.

**PR7.** WHEN two deliveries of the **same** `eventId` for the same order are applied concurrently — from separate `MongoClient` instances, not one pool — THE SYSTEM SHALL apply exactly one and report the other `Duplicate`: the losing `findAndModify`'s predicate is re-evaluated by the storage engine after the write conflict, finds its key present, matches nothing and returns `null`. WHEN two deliveries of **different** `eventId`s for the same **absent** order are applied concurrently, THE SYSTEM SHALL end with exactly one document containing both timeline entries: at most one insert wins, and IF the losing upsert surfaces a duplicate-key error on `_id` — a `MongoWriteException` whose `WriteError.Category` is `ServerErrorCategory.DuplicateKey` — THEN THE SYSTEM SHALL retry that one operation exactly once, after which it can only match, and SHALL NOT surface the error to the consumer. Every other error propagates so the fact is redelivered.

**PR8.** WHEN a fact is applied to an order that has no document, THE SYSTEM SHALL create one whose `_id` and `orderId` are the fact's `correlationId` as a lowercase hyphenated GUID string, whose `headerComplete` is `false`, whose `status` is `placed` with `statusRank` **0**, whose `timelineOrderVersion` is the current version, whose `events`, `processedEventKeys` and `items` are empty arrays, whose `updatedAt` is the triggering fact's own `occurredAt`, and whose `orderReference`, `orderDate`, `cancellationReason`, `currency`, every field of `retailer`, `company`, `totals` and `references` are **explicit `null`s** (the shape #7's `placeholderSkeleton` wrote and `openapi.yaml` `OrderDetail` tolerates); and SHALL then apply the fact by the same pipeline it applies to a pre-existing document (`R53`). Rank `0` is strictly below `order.placed.v1`'s rank `1`, so the real fact still writes.

**PR9.** THE SYSTEM SHALL set `headerComplete` to `true` **only** when `order.placed.v1` is applied, in the same atomic apply that writes `orderReference`, `orderDate`, `retailer.code`/`retailer.gln`, `company.code`/`company.gln`, `currency`, `totals` and `items` **unconditionally** (no `$ifNull` — `order.placed.v1` occurs once per order and the dedup filter stops its redelivery; a conditional write would hide two different `order.placed.v1` facts for one order behind a silent no-op); WHILE `headerComplete` is `false` the document SHALL still be a valid `OrderDetail` (`orderId`, `status`, `events`, `updatedAt` present). `retailer.name`, `company.name` and `items[].name` are **not** on any fact and stay `null` in a projected document — `R54` forbids the master-data lookup that would fill them, exactly as in #7; a seeded document carries them because the seed has the master data in hand (`PR44` lists this as an expected difference).

**PR10.** THE SYSTEM SHALL store the `events` array sorted by the **causal timeline order** below, re-sorting the array **in full** inside the atomic apply on every write, so `R50`'s and `R28`'s ordering is a property of the stored document — not of the query that reads it, and not of the order in which facts arrived:

1. **Primary key — `occurredAt` ascending.** Two entries whose `occurredAt` differ are ordered by that value alone; clauses 2 – 5 never reorder across that boundary.
2. **Tie group.** A maximal set of entries of one document whose `occurredAt` values are identical. Ties are the normal shape of a causal step within one instant: a derived fact reuses its triggering fact's `occurredAt` verbatim (Orders' `SagaStepTable`/`SagaFactHandler`, which pass `fact.OccurredAt` straight into the transition; Billing's completion pair, `progress/impl_completion_pair_has_no_causal_edge.md`).
3. **Causal edge.** Within tie group `G`, `p` is the cause of `c` IF AND ONLY IF `c.causationId == p.eventId` AND `p ∈ G` AND `p ≠ c`. Every entry has at most one cause, so the relation restricted to `G` is a forest in every well-formed history.
4. **Causal depth.** `0` where `e` has no cause in `G`, `1 + depth(cause(e))` otherwise, evaluated as a fixpoint over **at most `|G|` relaxation rounds**, each round recomputing every entry's depth simultaneously from the array as it stood at the start of the round.
5. **Within a tie group — depth ascending, then `eventId` ascending.** A fact is therefore always stored **after** the fact that caused it, and the order is total.

THE SYSTEM SHALL NOT infer a causal edge from `eventType`, from an implied status, from a status rank, or from any other property of the fact: an edge exists **only** where one entry's `causationId` is literally another entry's `eventId`. The depth is computed and discarded inside the pipeline stage; it is never stored.

**PR30.** THE SYSTEM SHALL store the triggering envelope's `causationId` verbatim, as a lowercase hyphenated GUID string, on **every** timeline entry it appends, and SHALL store **no** ordering key derived from `eventType` on any entry. `PR12`'s `statusRank` remains document-level and is used only for `R52`'s "precedes"; it SHALL NOT be used, directly or transformed, as a timeline ordering key.

**PR31.** THE SYSTEM SHALL make `PR10`'s order **total and defined for every possible stored entry set**, without erroring, dropping, duplicating, or depending on anything outside the document: IF an entry's `causationId` names something that is not in its own tie group (a different tie group, a fact never received, a command id, no entry at all), THEN that entry has no cause, depth `0`, and the fallback places it; IF the causal relation within a tie group contains a **cycle**, THEN the bounded fixpoint SHALL still terminate with a deterministic total order, every entry present exactly once, no throw, no loop, no discard; WHERE two tied entries are separated by no edge — independent facts, or two **siblings** sharing one `causationId` — THE SYSTEM SHALL order them by `eventId` ascending, a documented fallback rather than an accident. IF an entry carries **no** `causationId` at all (a document written by hand, or by a future writer that omits it), THEN the pipeline SHALL treat it as cause-less (`$ifNull`) rather than fail.

**PR11.** THE SYSTEM SHALL write a reference field (`references.despatchReference`, `references.invoiceReference`, `references.paymentReference`) **only while it is `null`**, evaluated inside the atomic apply, and SHALL never overwrite a non-null reference (`R52`). Each of the three reference-carrying facts fills only its own field.

**PR12.** THE SYSTEM SHALL derive each fact's implied order status and status rank from exactly this table, SHALL raise `status`/`statusRank` to the new value **only when the new rank is strictly greater** than the stored rank, and SHALL leave both untouched for every fact whose implied status is none (`R52`):

| `eventType` | Implied status | Rank |
|---|---|---:|
| `order.placed.v1` | `placed` | 1 |
| `stock.reserved.v1` | `stock_reserved` | 2 |
| `credit.approved.v1` | `credit_approved` | 3 |
| `order.confirmed.v1` | `confirmed` | 4 |
| `order.despatched.v1` | `despatched` | 5 |
| `invoice.issued.v1` | `invoiced` | 6 |
| `payment.received.v1` | `paid` | 7 |
| `order.completed.v1` | `completed` | 98 |
| `order.cancelled.v1` | `cancelled` | 99 |
| `stock.rejected.v1`, `stock.released.v1`, `credit.rejected.v1`, `credit.released.v1`, `order.saga_failed.v1` | *(none)* | 0 |

Ranks 1 – 7 are the state machine's linear progression; `completed`/`cancelled` are terminal and mutually unreachable, ranked highest and distinct so the projection is total; the five status-less facts contribute rank `0` and touch neither field. The nine status→rank pairs SHALL equal `MongoSeedWriter`'s own copy (`PR40`).

**PR13.** THE SYSTEM SHALL set `cancellationReason` from `order.cancelled.v1`'s payload only, and only while it is `null`.

**PR14.** THE SYSTEM SHALL set `updatedAt` to the **greatest `occurredAt` applied so far** (`$max` over the stored and incoming wire strings, which orders chronologically only because both are rendered in one fixed format — `PR41`), never the wall clock and never an arrival time. `MongoSeedWriter` writes exactly this value (`saga.UpdatedAt` is the last fact's `occurredAt`).

**PR15.** THE SYSTEM SHALL make every field of a read-model document a **pure function of the set of facts applied to it** — independent of arrival order, of delivery count, of the wall clock and of any generated identifier. Consuming a topic twice, or a shuffled permutation of it with arbitrary duplicates, SHALL produce a BSON-identical document. Specifically: `updatedAt` from `occurredAt` (`PR14`); `events` by `PR10`'s rule, a function of the stored entry set as a whole, **recomputed in full on every apply**, so a fact arriving *before* the fact that caused it yields the identical final array as the reverse arrival; `processedEventKeys` stored **sorted** (`$sortArray`, binary order — the same order `StringComparer.Ordinal` gives the seed's keys); `_id` is the fact's `correlationId`; **no identifier is generated anywhere in this service** — `UniqueId.New`/`Guid.NewGuid` appears nowhere under `src/Projector/`; no counter, arrival index or partition/offset field exists on the document.

### 2.3 The human-readable summary (`R50`)

**PR16.** THE SYSTEM SHALL build the timeline entry's `summary` — and its optional `detail` — for each of the fourteen facts from the **envelope alone**, in a pure domain function with no read-model access, no write-model access and no clock; SHALL render every monetary value from `long` minor units together with the payload's own `currency`, never as a floating-point number, never `decimal`, never converted (`"16 130 EUR"` — digits grouped in threes by a space, then the code, #7's `formatMinorUnits` byte for byte, because a projected document in #8 must read as a projected document in #7); and SHALL produce the **same fourteen strings #7's `summaries.ts` produces** for the same payloads, with `detail` populated only for `stock.rejected.v1` (`shortages`, `reason`), `stock.released.v1` (`released`, `reason`), `credit.rejected.v1` (`reason`, `requestedAmount`), `order.cancelled.v1` (`cancellationReason`, `compensationSteps`) and `order.saga_failed.v1` (`command`, `attempts`, `lastError`). The seed's nine summaries share this voice but not its thousands grouping (`"16130 EUR"`) — an inherited #7 difference, recorded in `PR44`, not repaired here.

### 2.4 The update signal (`R55`)

**PR17.** THE SYSTEM SHALL announce every applied change by **publishing** two messages on the shared singleton `INatsConnection` using core NATS publish — fire-and-forget, no reply subject, no responder — on `readmodel.order.updated.<orderId>` and `readmodel.timeline.appended.<orderId>`, carrying respectively `openapi.yaml`'s `OrderStreamUpdate` and `TimelineStreamEntry` shapes (the latter **with `causationId`**, `PR33`), serialised with `JsonWire.Options` (camelCase, nulls omitted), and carrying `x-correlation-id = <orderId>` in a **fresh** `NatsHeaders` per publish. The `<orderId>` token makes feature 25's `?orderId=` filter a subscription and its omission a wildcard.

**PR18.** THE SYSTEM SHALL publish the update signal **only after** the atomic apply has returned a document — and only then: a redelivery the filter suppressed (`R51`) returns `null`, invokes no post-apply callback and produces no signal. Both payloads are built from the **post-apply** document (`PR42`), so a signal can never describe a state the store never held.

**PR19.** IF publishing the update signal fails, THEN THE SYSTEM SHALL log one structured error carrying `eventId`, `correlationId`, `orderId` and both subjects, SHALL **not** rethrow, and SHALL acknowledge the fact. Rethrowing is strictly worse: the projection has already applied, so the redelivery is suppressed by `PR6`'s filter and could never emit the signal on a later attempt — a guaranteed-failing retry that blocks the partition. The loss is bounded and already accounted for by `openapi.yaml` `/orders/stream` (bounded buffer, client re-fetches, the read model is the source of truth).

### 2.5 Sole writer, and no write-model access (`R54`)

**PR20.** THE SYSTEM SHALL make `src/Projector` the only **runtime** writer of `order_timeline`: within `src/`, only `src/Projector` and `src/Seed` may invoke a MongoDB.Driver **write-shaped** operation (`InsertOne*`, `InsertMany*`, `UpdateOne*`, `UpdateMany*`, `ReplaceOne*`, `FindOneAndUpdate*`, `FindOneAndReplace*`, `FindOneAndDelete*`, `DeleteOne*`, `DeleteMany*`, `BulkWrite*`, `Indexes.CreateOne*`/`CreateMany*`, `Drop*`), `src/Seed` allow-listed **by name with its reason inside the guard** (an offline fixture loader, never deployed, run before the system runs, writing documents in exactly the shape this feature specifies). The guard SHALL scan production source only (no `tests/`), SHALL fail when any other `src/<Service>` acquires a write-shaped call, SHALL **permit a read** anywhere — `R54`'s own second half obliges the Gateway to read this collection — and SHALL prove its non-vacuity against a scratch source tree rather than by assertion. Its two stated limitations (a same-name unrelated method is a false positive; `$merge`/`$out` inside an `Aggregate` is a false negative) are recorded in its header, as #7's amended guard records them.

**PR21.** THE SYSTEM SHALL give the projector **no** access to any write model: no `Microsoft.EntityFrameworkCore.*` or `Microsoft.Data.SqlClient` package reference in `Projector.csproj`, no `ProcessedEventConfiguration.cs`, no `DbContext`, and no NATS **request** to any `orders.*`, `fulfillment.*`, `billing.*` or `catalog.*` subject. Everything the read model contains SHALL come from fact payloads. The projector SHALL expose **no HTTP surface** — Notifications is the precedent; readiness is feature 27's.

**PR22.** THE SYSTEM SHALL create the read model's indexes idempotently at boot, before the first poll (`PR43`): the uniqueness index on `orderReference` SHALL be **partial** (`partialFilterExpression: { orderReference: { $type: "string" } }`, name `uq_order_reference`) because a placeholder carries `orderReference: null` and MongoDB compares indexed nulls equal, so a plain unique index would reject the **second** placeholder; and `ix_status_updatedAt` (`{ status: 1, updatedAt: -1 }`) for feature 25's list query. IF an index of the same name exists with different options (`IndexOptionsConflict`, code 85), THEN the projector SHALL fail to start with a message naming the index and the `dropIndex` one-liner, rather than silently run against it. **`src/Seed` already creates `uq_order_reference` partially** (`MongoSeedWriter.EnsureIndexesAsync`, phase 5), so unlike #7 no seed edit is needed — but the two definitions must stay identical (`PR39`).

### 2.6 The idempotent-consumer variant, and the parity guard

**PR23.** THE SYSTEM SHALL implement the idempotent-consumer pattern (`R17`, `R18`, `saga.md` §6 layer 1) as a **documented variant** whose ledger is the read-model document itself: the pair `"projector:<eventId>"` in `processedEventKeys`, written by the same single operation that applies the projection (`PR6`). The mark and the effect are not two writes in one transaction; they are **one write** — which is why a fifth MS-SQL database was rejected (design §9.1) and why the compose stack's **standalone** `mongo:8.3.8` (no replica set, no multi-document transactions) costs nothing here.

**PR24.** THE SYSTEM SHALL keep `tests/Orders.UnitTests/IdempotentConsumerParityTests.cs` true of itself with **no edit to that file or to any file under `src/Orders` or `tests/Orders.*`**: the projector SHALL own **no** `Infrastructure/Persistence/Configurations/ProcessedEventConfiguration.cs` (so `DiscoverCopyServices` and case 3 never select it, and case 1's byte-identity set stays `{Orders, Notifications}`), and SHALL own `src/Projector/Infrastructure/Messaging/IdempotentConsumer.cs` — type name `IdempotentConsumer`, because `.editorconfig` requires the file to match the type — whose leading banner cites the canonical path literal `src/Orders/Infrastructure/Messaging/IdempotentConsumer.cs`, carries a `Divergence:` line stating what differs and why, and carries a `Behavioural conformance: tests/Projector.IntegrationTests/IdempotentConsumerConformanceTests.cs` line naming a file that **exists**. The parity guard's case 4 (`RequiresADocumentedDivergenceBanner…`) has had **no subject** since it was written; this feature is its first, and the guard checks only the first two lines — the third is asserted by the projector's own structural test (`PR24`'s row in §3), which also asserts the named file exists.

**PR25.** THE SYSTEM SHALL prove the variant against the **five behavioural conformance cases** of `outbox_and_idempotency` design.md §6 — #8 has no generic copyable suite, so the five are written directly — over **real MongoDB via Testcontainers**: (1) a first call runs the post-apply work once and reports `Processed`; (2) a second call for the same `(eventId, consumer)` does **not** run it and reports `Duplicate`; (3) a consumer constructed **fresh over the same backing store** still reports `Duplicate` — the in-memory failure feature 23's #7 counterpart shipped; (4) two distinct `eventId`s both run; (5) the same `eventId` under a **different** consumer name runs — why the key is the pair and not the bare id already in `events[]`.

**PR26.** WHILE the conformance cases run, the subject SHALL be the **real** `IdempotentConsumer` over the **real** driver, the pipeline a dedup-only `$set` of the key, and the "work" the variant's **post-apply callback** — invoked exactly once on `Processed` and **not at all** on `Duplicate` (a counter, not the document's residue — `N10`). Idempotency is what these cases prove; `R50` – `R53` prove the projection.

### 2.7 The application shape

**PR27.** THE SYSTEM SHALL route every fact through the hand-rolled dispatcher (`src/Cqrs`, binding across all six services) as **one** `ProjectFactCommand : ICommand` carrying the domain `FactEnvelope`, handled by **one** `ICommandHandler<ProjectFactCommand>` that delegates to `ProjectionApplyService` with no branching on `eventType` — not fourteen command classes, because the projector's behaviour is uniform in `eventType`: all fourteen variations live inside the pure `FactProjection.Project`. Every port SHALL be registered explicitly in `AddProjector(...)`; `AddDispatcher` runs last so a missing or duplicated handler is a boot failure (`ValidateOnBuild`/`ValidateScopes` forced on, the `NotificationsHost` shape).

**PR28.** THE SYSTEM SHALL keep `OrderToCash.Projector.Domain` free of every framework and store dependency — `MongoDB.*`, `NATS.*`, `Confluent.Kafka`, `System.Text.Json`, `Microsoft.EntityFrameworkCore`, `OrderToCash.Cqrs`, `decimal` — by expressing a fact's effect as a store-agnostic **`ProjectionDelta`** value (the entry, the implied status and rank, the reference and header fields it may fill) that Infrastructure alone translates into `PR6`'s pipeline. The domain's input is its own `FactEnvelope` record (`EventId`, `EventType`, `CorrelationId`, `CausationId`, `OccurredAt`, `object Payload`) whose payload is one of `Contracts.Facts.Payloads.*` — plain records, no serialiser dependency. Enforced by the existing `DomainPurityTests`/`CqrsDomainPurityTests`/`DomainDecimalTests`, which already enumerate `OrderToCash.Projector.Domain` (the `ProjectorDomainPlaceholder` type SHALL be kept so `DomainAssemblies.All` still compiles).

### 2.8 Migration, and the wire (from A1)

**PR32.** WHEN the projector starts, THE SYSTEM SHALL bring every stored document's `events` order to the **current timeline-order version** before consuming any fact, selecting documents by `{ timelineOrderVersion: { $ne: <current> } }` — **never** by the presence or absence of a field. WHERE a stamp is absent or differs, THE SYSTEM SHALL re-sort `events` by `PR10`'s current rule with the **same** pipeline expression the live apply uses, stamp the version, and touch no other client-visible field; WHERE it already equals the current version, THE SYSTEM SHALL make no write. IF the rule later changes, THEN incrementing the constant SHALL be sufficient to re-sort every document. Today every document any writer in #8 has ever produced is at version `2` (`PR40`), so the live path is a no-op; the guard test constructs a version-`1` document by hand.

**PR35.** THE SYSTEM SHALL NOT invent a `causationId` for an entry that has none, and SHALL NOT infer one from `eventType`, arrival order or array position. The migration's boot log SHALL report the number of documents migrated **and** the number of them still holding an entry with no `causationId`.

**PR33.** THE SYSTEM SHALL treat a timeline entry's `causationId` as **part of the public read contract** — #7's gate ruled it public and `specs/shared/openapi.yaml` as inherited already carries it on `TimelineEntry` and `TimelineStreamEntry` — so the projector stores it on every entry (`PR30`), carries it on every `timeline.appended` signal (`PR17`), and projects it out **nowhere**. `statusRank`, `processedEventKeys` and `timelineOrderVersion` remain internal and are feature 25's to exclude from every read (`{ statusRank: 0, processedEventKeys: 0, timelineOrderVersion: 0 }`), recorded here so feature 25 does not rediscover it.

**PR34.** WHERE the seed writes fixture documents into the same collection, each entry SHALL carry `causationId` from the fixture's own declared chain and the document SHALL be stamped at the current version. **Already satisfied by inheritance**: `MongoSeedWriter.ToTimelineDocument` has written both since its first commit (`181060f`). No seed edit.

### 2.9 New to #8 — each names why #7 could not have faced it

**PR36 — routing has one source of truth.** THE SYSTEM SHALL decide *which* facts it handles and *how* their payloads are typed from **one** table — `FactCatalog.PayloadTypesByEventType` — with no second list of `eventType` strings anywhere under `src/Projector/`: the consumer looks the type up there, deserialises the payload to that CLR type with `JsonWire.Options`, and the domain's `FactProjection.Project` switches on the **payload's CLR type** (fourteen arms, no default that returns). A `grep` of `src/Projector/` for the fourteen `eventType` literals SHALL return hits only in test-facing constants and log messages, never in a routing structure. *Why new:* Notifications (#8 feature 23, review round 1 D1) shipped a `HashSet` filter beside a routing `switch`; deleting a filter entry stopped a fact being handled with both suites green. #7's projector had a `HANDLED_EVENT_TYPES` array beside its switch — the same two-list shape, unbitten only by luck.

**PR37 — every copied envelope field is corruption-guarded.** THE SYSTEM SHALL carry `eventId`, `eventType`, `correlationId`, `causationId` and `occurredAt` from the wire envelope onto the domain `FactEnvelope`, onto the stored timeline entry and onto both signal payloads such that corrupting **any one** copied field at any one hop fails a named test with a sentinel value the test supplied. *Why new:* backlog id 58 — Notifications' hand-written `ToEnvelope` copy survived corruption of its `correlationId` on a green suite. The projector's copy is the same shape, and the timeline is where a wrong `causationId` becomes a wrong order.

**PR38 — the consumer configuration is asserted, not argued.** THE SYSTEM SHALL build its `ConsumerConfig` with `GroupId == ConsumerNames.ToToken(ConsumerName.Projector) == "projector"`, `ClientId == "otc-projector"`, `AutoOffsetReset.Earliest`, `EnableAutoCommit == true`, `EnableAutoOffsetStore == false`, and SHALL store an offset **only after** the handler completes — proven by a reflection test reading the same private `BuildConsumerConfig` the runtime calls (the Notifications D3 shape) and by an integration case where a throwing handler leaves the committed offset unchanged, **read from the broker**, never inferred from a redelivery. *Why new:* #7's `fromBeginning: true` was a kafkajs subscribe option asserted by `main-kafka-options.spec.ts`; in Confluent.Kafka the equivalent is a config token whose **default is `Latest`**, and Notifications' D3 finding was that this exact token was argued in prose and asserted by nothing.

**PR39 — the index definition is the seed's, byte for byte.** THE SYSTEM SHALL create `uq_order_reference` with keys, uniqueness, name and partial filter identical to `MongoSeedWriter.EnsureIndexesAsync`'s, such that running the seed's creation then the projector's, **or the projector's then the seed's**, on one collection raises no `IndexOptionsConflict`. *Why new:* in #7 the seed was edited to match the projector at the gate; in #8 the seed landed first with the partial index already in place, so the projector must match it, and two independently-typed `CreateIndexOptions` are the failure mode.

**PR40 — constants shared with the seed writer are asserted equal.** THE SYSTEM SHALL keep its `TimelineOrderVersion` equal to `MongoSeedWriter.TimelineOrderVersion` (`2`) and its nine status→rank pairs equal to `MongoSeedWriter`'s private table, asserted by tests that read **both** values, so a bump on one side without the other is a red test, not a boot-time migration of every seeded document. *Why new:* `MongoSeedWriter.cs`'s own comment says it is *"a local copy of the projector's own `TIMELINE_ORDER_VERSION`"* — a copy nothing checked, because the original did not exist yet.

**PR41 — the BSON rendering is fixed, not defaulted.** THE SYSTEM SHALL write element names as **camelCase string literals** equal to `OrderTimelineDocument`'s `[BsonElement]` names (`_id`, `orderId`, `orderReference`, `orderDate`, `retailer.code/name/gln`, `company.*`, `status`, `cancellationReason`, `currency`, `totals.initialAmount/initialDiscount/totalAmount`, `items[].productCode/name/quantity/unitPrice/lineDiscount`, `references.despatchReference/invoiceReference/paymentReference`, `events[].eventId/eventType/occurredAt/summary/detail/causationId`, `headerComplete`, `updatedAt`, `statusRank`, `timelineOrderVersion`, `processedEventKeys`); every id as `Guid.ToString("D")` (lowercase, hyphenated — never the BSON UUID subtype); every instant in `InstantJsonConverter`'s wire format (`yyyy-MM-dd'T'HH:mm:ss.fff'Z'`, exactly three fraction digits, literal `Z` — never `"O"`, which would break `PR14`'s `$max` and `PR10`'s string sort); `totals.*`, `items[].unitPrice`, `items[].lineDiscount` as **BSON Int64**; `items[].quantity` as Int32; `detail` rendered through `JsonWire.Options` into a `BsonDocument` (camelCase keys, integers kept lossless — a value above `int.MaxValue` is Int64 with the same value, never truncated); `detail` **absent** when the fact has none, explicit `null` for the placeholder's unknown scalars. *Why new:* #7 got camelCase from JavaScript object literals, string ids and ISO strings from `.toISOString()`, and numeric width from the node driver's defaults; the C# driver's defaults are PascalCase element names, BSON UUID subtype for `Guid`, `DateTime` for instants and `Int64` for `long` — four silent divergences from the seed's documents and from #7's.

**PR42 — the signal describes the post-apply state.** THE SYSTEM SHALL call `FindOneAndUpdateAsync` with `ReturnDocument.After`, and the `order.updated` signal's `status`, `references` and `cancellationReason` SHALL equal the document's stored values after the apply. *Why new:* the C# driver's `FindOneAndUpdateOptions.ReturnDocument` **defaults to `Before`**; #7 passed `returnDocument: 'after'` explicitly. With the default, duplicate detection still works (a non-match is still `null`) but every signal would carry the *previous* status — correct on the path a deletion probe takes, wrong on the wire.

**PR43 — boot ordering is a hosted-service contract.** THE SYSTEM SHALL run index creation (`PR22`) and the timeline-order migration (`PR32`) to completion in a `ReadModelBootstrap : IHostedService` registered **before** `ProjectorFactsConsumer`, with hosted-service startup sequential (the host default; `ServicesStartConcurrently` SHALL stay `false`), so the consumer's first `Consume` cannot precede the bootstrap's return. IF the bootstrap throws, THEN the host SHALL fail to start. *Why new:* #7's `main.ts` awaited both before `startAllMicroservices()` in one function; in .NET the ordering is a property of registration order and host options, both of which can be reordered without a compile error.

**PR44 — the seed's own documents are the parity oracle.** THE SYSTEM SHALL, for each of the six seeded sagas, project that saga's own outbox facts (`OrderSagaFixture.OrdersOutbox` + `.FulfillmentOutbox` + `.BillingOutbox`, payloads already typed) through the real writer into an empty collection and produce a document equal to `MongoSeedWriter.ToTimelineDocument(saga)` on every field **except** the following enumerated set, each with its reason: `retailer.name`, `company.name`, `items[].name` (master data, not on any fact — `PR9`); `events[].summary` for `credit.approved.v1` and `credit.rejected.v1` (#7's projector groups thousands, its seed did not — `PR16`); `events[].detail` (the seed's fixtures carry a hand-written subset of #7's projector `detail` — `PR16`'s builders are the oracle for `detail`, the seed is not). Everything else — ids, `orderReference`, `orderDate`, `status`, `statusRank`, `currency`, `totals`, `items` minus `name`, `references`, `events[]` order, `eventId`, `eventType`, `occurredAt`, `causationId`, `headerComplete`, `updatedAt`, `timelineOrderVersion`, `processedEventKeys` — SHALL be equal, **including BSON types**. *Why new:* #8's seed wrote its documents first and proved them byte-identical to #7's (`tests/Seed.IntegrationTests/OracleFixtures/order_timeline_from_number7.json`); that makes the seed the cheapest available oracle for the projector, one #7 never had at implementation time.

### 2.10 Deliberately **not** reused from #7

**`PR29` (the legacy-document backfill) is not ported, and its id is not reused.** #7 needed it because `apps/seed` had written documents **without** `statusRank` and `processedEventKeys` for seven phases before the projector existed; replaying over such a document appended every fact a second time and regressed a terminal status (`progress/review_projector_read_model.md` probe 3 proved it live). In #8 that document shape has never existed: `src/Seed/Infrastructure/Mongo/MongoSeedWriter.cs` has exactly one commit (`git log --oneline -- src/Seed/Infrastructure/Mongo/` → `181060f`), and that revision already writes `statusRank`, `processedEventKeys`, `timelineOrderVersion`, `events[].causationId` and the partial index (`git show 181060f:src/Seed/Infrastructure/Mongo/MongoSeedWriter.cs | grep -c "TimelineOrderVersion\|CausationId\|ProcessedEventKeys\|PartialFilterExpression"` → `5`). `R54` forbids any other writer, and `PR20` guards it. A backfill filtered on `{ statusRank: { $exists: false } }` therefore has no document it could ever match, and a guard test for it would have to fabricate a shape no writer produces — the definition of a decorative guard. What **is** kept: `PR6`'s pipeline stays total over any document shape (`$ifNull` on every array and rank operand), so an odd document is never fatal; and `PR32`'s version-stamped migration, which is the forward-looking mechanism, is kept in full.

## 5. Out of scope — restated so it is a decision, not an omission

- **No HTTP surface, no health endpoint** (`PR21`). Readiness indicators are feature 27's; Notifications set the precedent of a plain host.
- **No SSE, no replay buffer** — `PR17` publishes and stops.
- **No dead-letter handling** (`R16`) beyond `PR3`/`PR4`'s log-and-acknowledge; retry counting and `.dlq` are feature 27's. Noted for 27: a duplicate-key error on `uq_order_reference` during the Phase-2 apply (two distinct order ids carrying one `orderReference`) is unreachable while `ORD-######` is unique and would be a poison pill if it ever occurred — #7's review N8, carried verbatim.
- **No OpenTelemetry** (`R56` – `R58`).
- **No change to any fact payload, topic, or envelope.** The only new wire vocabulary is `PR17`'s two subjects, which `asyncapi.yaml` does not declare — inherited from #7's gate row 2 exactly as #7 shipped it.
- **No edit under `src/Orders`, `tests/Orders.*`, `src/Seed`, `tests/Seed.*`, `src/Notifications`, `tests/Notifications.*`, `src/Gateway`, `apps/web`** — with two named exceptions: `OrderToCash.sln` gains the two test projects, and `tests/Projector.*` project files reference `src/Seed` (read-only, as `PR40`/`PR44`'s oracle).
- **Backlog ids 58 and 59 do not ride this feature.** Both are Notifications-file work (`NotificationFactsConsumer.ToEnvelope`; the date-typed payload sweep over Notifications' templates). `PR37` applies id 58's *lesson* to the projector's own copy from the start; it does not fix Notifications' copy, and claiming it did would be a scope lie.
- **No hardening of `IdempotentConsumerParityTests` case 1's membership** (Phase 11's closing note, *"assert the discovered set against a declared expected membership at the moment the third copy lands"*): the projector is a **variant**, not a copy, so it is not that third member; the note's trigger has not fired.
